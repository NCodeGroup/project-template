## Work in the plan's worktree

Each plan lives in its own git worktree, so several Claude Code sessions can work on different plans on this machine at once. Before anything else, move this session to the plan:

1. Run `git rev-parse --show-toplevel`. If the path contains `/.claude/worktrees/` and has a `PLAN.md`, this session is in the plan's worktree: go on with the task.
2. Otherwise list the plan worktrees: run `git worktree list --porcelain`, keep each `worktree` path under `.claude/worktrees/` that has a `PLAN.md`, and read each plan's title from its first line.
3. Choose the plan, in this order: the worktree whose folder name the command's arguments give; else the only plan worktree; else, when there is no plan worktree, the `PLAN.md` in the current checkout, worked on where it is — a plan written without a worktree, such as in Copilot. Switch into a chosen worktree with the `EnterWorktree` tool and its `path`. With several plan worktrees and none named, list them with their titles and stop to ask which one. With no plan anywhere, stop and say so.

From here on, the plan's folder is the repository root: run every command there, Done-when commands included. In a worktree, never edit files or run git in the main checkout. When you delegate to a subagent, give it the folder's absolute path and tell it to work only there.

## Task

Land the plan in `PLAN.md` the way this repository's Landing policy says: push its commits to the default branch or open its pull request, tag and publish its release, comment on and close its issue, and file its follow-ups as issues. Run it again at any time: each stage checks whether it is done and skips it, so a run that stopped partway, or a pull request that has merged since, carries on where it left off. Never force-push, rebase onto a moved default branch, move or delete a tag, or delete a release.

Extra instructions (may be empty): $ARGUMENTS

1. Read the state: run `pwsh -NoProfile -File .template/Get-PlanState.ps1` from the repository root. It prints `key: value` lines. Below, `<default>` is its `default` value, `<branch>` its `branch` and `<version>` its `release`. Stop and say what to run instead when `plan` is `-`; when `dirty` is `yes`; when `steps` shows an open, escalated or failed step (run orchestrate-plan, or replan-step); when `reviewed` isn't `current`, because the work changed since its last clean review or never had one (run review-plan-diff); or when `next` is `finish-plan`, because everything is done (run finish-plan).
2. Read the policy from the `landing` line: `integrate` is `direct` or `pull-request`, `release` is `none`, `tag` or `tag+release`, and `changelog` names the changelog file. Read `PLAN.md`'s title, `Issue:` line, Goal, Decisions and `## Follow-ups`. When `release` isn't `none`, stop when `<version>` is `-`, because the plan has no `Release:` line, or when the changelog's first `## ` heading isn't `## <version>`. When `tag` is `present`, it must already point at the commit this plan lands; otherwise stop, because a tag is never moved. When the `## Landing` section of `AGENTS.md` has `- protect: hook` and `integrate` is `direct`, stop: the `pre-push` hook refuses a push to `<default>`, so set `integrate: pull-request`.
3. With `integrate: direct`, stop when `behind` is more than 0: the default branch moved since the plan branched, so bring it in, run the checks and the review again, then ship. With `integrate: pull-request`, `behind` doesn't matter, because the pull request merges it.
4. Show the landing summary, then ask me once whether to go ahead and wait for my answer. The summary lists: the commits to land (`git log --oneline origin/<default>..HEAD`), and the empty `Plan:` and `Re-plan step` commits among them that will be dropped; where they go, the default branch or a pull request from `<branch>`; the tag and the release; what the issue gets; and each follow-up, which is filed as an issue labelled `follow-up` once the plan has landed unless I name it as one to drop. After my yes, append ` — dropped` to the line in `PLAN.md` of each follow-up I named, then run every stage below without asking again. `git push` may still ask for its own approval.
5. Drop the empty commits when `landed` is `no` and the branch has never been pushed (`git rev-parse --abbrev-ref '@{u}'` fails): `git rebase -f --no-keep-empty (git merge-base HEAD origin/<default>)`. It changes no file, so the review still matches. Skip it when the branch has an upstream, because rewriting pushed commits needs a force-push.
6. Land the commits, unless `landed` is `yes`:
   - `direct`: when `release` isn't `none` and `tag` is `absent`, tag the commit first: `git tag -a <version> -m <version>`. Then push the commits and the tag together, so both land or neither does: `git push --atomic origin HEAD:refs/heads/<default> refs/tags/<version>`, or `git push origin HEAD:refs/heads/<default>` when there is no tag. A rejected push means the default branch moved: stop, as in item 3.
   - `pull-request`, when `pr` is `-` or `CLOSED`: push the branch with `git push -u origin HEAD`, then open the pull request. Its title is the plan's title. Its description is two to five lines summarizing the plan's steps and Decisions, then `Closes <issue reference>` on a line of its own when the plan has an `Issue:` line. GitHub: `gh pr create --base <default> --head <branch> --title "<title>" --body-file <file>`. GitLab, when `host` is `gitlab`: `glab mr create --source-branch <branch> --target-branch <default> --title "<title>" --description (Get-Content -Raw <file>) --yes`. When the extra instructions say `draft`, open it as a draft: add `--draft` to either command.
   - `pull-request`, when `pr` is `OPEN`: stop here. Say the pull request waits for review and merge, give its URL, and say that running ship-plan again after the merge tags, publishes and closes what's left.
   - `pull-request`, when `pr` is `MERGED`: stop. The pull request merged, but without this branch's `HEAD`, so commits were added after it. Give the state script's `next` and say to land those commits from a new branch.
7. Tag when `release` isn't `none` and `tag` is still `absent`, as it is after a pull request merged. Tag the commit the pull request merged as: on GitHub, `gh pr view <number> --json mergeCommit --jq .mergeCommit.oid`; on GitLab, the merge request's `merge_commit_sha`, or `squash_commit_sha` when that is empty, from `glab mr view <number> --output json`. Run `git fetch origin`, then `git tag -a <version> -m <version> <commit>` and `git push origin refs/tags/<version>`.
8. Publish when `release` is `tag+release` and `published` isn't `yes`. Write the changelog's `## <version>` section, without its heading and up to the next `## ` heading, to a file. Then on GitHub: `gh release create <version> --verify-tag --title <version> --notes-file <file>`; on GitLab: `glab release create <version> --name <version> --notes-file <file>`.
9. Close the issue when `issue-state` is `OPEN`: comment once, then close it. The comment says where the change landed (the release, or the commit or pull request), summarizes the Goal in two to four sentences, and lists the follow-ups not done. GitHub: `gh issue comment <number> --body-file <file>`, then `gh issue close <number>`. GitLab: `glab issue note <number> --message (Get-Content -Raw <file>)`, then `glab issue close <number>`. Add `--repo <owner/repo>` for an issue in another repository. A pull request that merged with `Closes` has already closed the issue, so `issue-state` is `CLOSED` and this stage is skipped.
10. File each follow-up I picked whose line doesn't end with `— filed as #<number>`: `gh issue create --title "<short title>" --body-file <file>`, or `glab issue create --title "<short title>" --description (Get-Content -Raw <file>)`. Then append ` — filed as #<number>` to its line in `PLAN.md`, so a second run doesn't file it again.
11. Write each comment, description, release note and issue body to a temporary file outside the repository with your file-writing tool, in a call of its own, and pass the file to the command. Never put the text in the command line. Delete the files in a separate command at the end.
12. Finish with each stage as done, skipped because it was already done, or waiting, with the links to the pull request, the release and the comment. Run the state script again and give its `next` as the next command: usually `/finish-plan`, which deletes `PLAN.md`, removes the plan's worktree and fast-forwards the default branch.
