# Project Template

Instructions for coding agents working on this repository: the project template itself, not a project made from it. [README.md](README.md) explains the repository. `PLAN.md`, when there is one, is the plan in progress. It is gitignored: never commit, stage or push it, and never use `git add -A`; stage the files a step lists. `/ship-plan` lands a reviewed plan by the Landing section below and keeps `PLAN.md` for `/finish-plan`, which deletes it. Before a push you were asked for and make without `/ship-plan`, delete `PLAN.md` once every step is marked `[x]`; when a step is still open, keep it and say which steps remain.

## Commits

- Commits and pull requests record the people who wrote them, so avoid AI agent attribution: don't add a `Co-authored-by:` trailer naming an AI agent (Copilot, Claude or any other), a `Claude-Session:` trailer or a "Generated with" line, and leave such lines out of the titles, descriptions and comments you write. Claude Code's `attribution` setting (`.claude/settings.json`) and VS Code's `git.addAICoAuthor` (`.vscode/settings.json`) are off here. Nothing checks for agent attribution or blocks a commit, push, pull request or pipeline that has it: when a tool adds it anyway, leave it, don't report it, and never rewrite history to remove it. Before your first commit in a clone or worktree, run `git config core.hooksPath`. When it prints nothing and the clone has no `.pre-commit-config.yaml` and no hook of its own in the folder `git rev-parse --git-path hooks` prints (a file whose name doesn't end in `.sample`), run `git config core.hooksPath template/.githooks`, so `template/.githooks/pre-push` runs; when it names a folder other than `template/.githooks`, or the clone has hooks of its own, never change it, and say that the hook doesn't run there.

## Tooling

This repository's own tooling follows the rule it gives every project, [ADR-0021](template/docs/decisions/project-template/0021-tooling-is-written-in-nodejs-then-go-then-powershell.md): write a script, a check or a generator in Node.js, or else in Go, or else in PowerShell 7, the first that fits the job. Node.js is the release `.node-version` names. The tests' Node.js checks live in `tests/node/`, whose `package.json` pins their packages exactly, and `brand/build.mjs` draws the logo kit. Python stays out of the tooling: the only Python here is Copier and pre-commit, Python programs the tests run, pinned in `tests/requirements.txt`.

## Plans

This repository keeps a plan's `Plan step N: <title>` commits on `main`: each is one verified change, and the template's workflow has no squash rule. A project that squashes them, such as one that merges its pull requests by squashing, does so in its own push protocol; taking changes only through pull requests doesn't require it, and this repository's `main` takes changes only through pull requests and keeps the step commits by merging with a merge commit or by rebasing. A plan's empty `Plan: <title>` and `Re-plan step N` commits change nothing, so drop them when the plan's branch lands. `/ship-plan` does this before it pushes: `git rebase -f --no-keep-empty` onto the branch's merge base with `origin/main`. By hand: `git rebase -f --no-keep-empty main` on that branch, then push it and open a pull request. Tagged history is never rewritten.

## Landing

`/ship-plan` pushes a reviewed plan's branch and opens a pull request into `main`, with `Closes` for the plan's issue. Merge it with a merge commit or by rebasing, not by squashing, so the plan's step commits stay on `main`. Once it merges, the Release workflow (`.github/workflows/release.yml`, which runs `template/.template/Publish-Release.ps1`, the script every GitHub project made from the template runs from `.github/workflows/tag-release.yml`) tags the commit it merged as with the plan's version, the newest section of `CHANGELOG.md`, and publishes the GitHub release from that section, so a Claude Code cloud session, whose GitHub proxy refuses a tag push, needn't do either. Running `/ship-plan` again after the merge finds the tag and the release done, and closes the plan's issue and files its follow-ups; it tags and publishes them itself only when the workflow hasn't, such as when its run failed. A plan's `Release:` line names the version, and its last step writes the changelog section. A release of this repository ships the template, everything a project made from it gets or runs: `template/`, `workflow/`, `tools/`, `copier.yml` and the scripts at the root. A plan that changes none of them, such as one that changes only `README.md`, `USAGE.md`, `CONTRIBUTING.md`, `AGENTS.md`, `tests/` or `.github/workflows/`, gets no `Release:` line, as the template's ADR-0032 says: its last step adds its entries under `## [Unreleased]`, and its merge tags and publishes nothing once the release before it is tagged and published. This repository is public. Its ruleset, Protect main, makes every change to `main` a pull request whose `test` check passes and whose every conversation is resolved, merged with a merge commit or by rebasing, and refuses force-pushes and deletion; Protect release tags refuses moving or deleting a `v*` tag. Every discussion on a pull request is remediated, fixed or answered with why nothing changed, and replied to before it merges (ADR-0014); an agent replies and never resolves a thread. Auto-merge is allowed for the person who marks a pull request ready, with a merge commit, never by an agent. `protect: hook` also has the template's `pre-push` hook refuse every push to `main` once a clone runs `git config core.hooksPath template/.githooks`, so a mistaken push stops before it leaves the PC. Never bypass it with `--no-verify`.

- integrate: pull-request
- release: tag+release
- changelog: CHANGELOG.md
- protect: hook
