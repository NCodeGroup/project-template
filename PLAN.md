# Plan: Adopt existing repositories into the template

## Goal
Existing repositories — about 13 NCodeGroup libraries built on the `NCode.ProjectSettings.Scaffold` NuGet package, NCode.Identity, and others — need the template's workflow and its updates, which today only `New-Project.ps1` projects get. This change adds `Adopt-Project.ps1`, which brings a repository under the template without asking questions: it works out the answers, runs Copier, rebuilds each merged file as the template's file plus the repository's own content (so later `Update-Project.ps1` runs merge instead of conflicting), extends `AGENTS.md` and `Directory.Build.props`, removes legacy setups through pluggable adapters, verifies the build, and commits. To make that fit public and library repositories, the template also gains a `workflow_tools` question (which of Claude Code, Copilot and the shack PC's local model a project gets) and an opt-in NuGet packaging option that replaces the scaffold.

## Context for the executor
- Build: none — PowerShell 7 scripts and a Copier template.
- Test: `.\Test-Template.ps1` renders the template and checks it (about 3 minutes in full; `-SkipDotnetBuild -SkipUpdate` takes about 1.5 minutes). From step 9 on, `.\Test-Adoption.ps1` tests adoption (`-UnitOnly` runs in seconds; `-SkipDotnetBuild` skips the .NET build and pack). Both print `PASS  <name>` or `FAIL  <name>` per check and end with `Template tests: PASSED` / `Adoption tests: PASSED`.
- Needs Copier on PATH (`uv tool install copier`), uv, Git with a global `user.name` and `user.email`, and the .NET SDK 10.0.402.
- Conventions: scripts start with comment-based help (`.SYNOPSIS`, `.DESCRIPTION`, `.EXAMPLE`) like `New-Project.ps1`, then `[CmdletBinding()]`, `param(...)` and `$ErrorActionPreference = 'Stop'`. Four-space indentation. Every file is UTF-8 without BOM with LF line endings; write files with `[IO.File]::WriteAllText($path, $text, [Text.UTF8Encoding]::new($false))`. Small helpers such as `Invoke-Copier` are copied into each script that needs them rather than shared — keep doing that. Comments are rare and explain why, in one line. Test checks use `Check '<name>' (<bool>) (<detail>)`, as in `Test-Template.ps1`; check names have no apostrophes. Docs use short plain sentences, tables, and sentence-case headings.
- Gotchas:
  - Files under `template/` are rendered by Copier only when their name ends in `.jinja`; every other file is copied byte for byte. Jinja `{%-` strips the newline before the tag; keep the rendered output of the default answers byte-identical unless a step says otherwise.
  - `template/.claude/commands/`, `template/.claude/agents/`, `template/.github/agents/`, `template/.github/prompts/` and `template/.github/skills/` are generated, and so are the same five folders at the repository root (this repository's own workflow): never edit them; change `workflow/` and run `.\Update-Template.ps1`, which regenerates both.
  - The update tests in `Test-Template.ps1` edit these exact strings in template sources, so they must stay: `Thumbs.db` in `.gitignore.jinja`, `"editorconfig.editorconfig"` in `.vscode/extensions.json.jinja`, `## Conventions` in `AGENTS.md.jinja` and `project-template.instructions.md.jinja`, `## AI-Assisted Workflow` in `README.md.jinja`, `## Claude Code` in `CLAUDE.md`.
  - Copier facts this plan relies on (all verified with Copier 9.19.1): `--data` reads values as YAML, so a list is passed as `[claude, copilot]`; a question whose `when` is false renders as its default (empty for no default) and isn't recorded; a question with no default and no answer fails `--defaults` with "Question ... is required"; `_exclude` patterns are Jinja-rendered and an empty pattern excludes nothing; `copier copy --overwrite` still keeps the `_skip_if_exists` files.
  - `ConvertFrom-Json -AsHashtable` returns ordered hashtables and accepts `//` comments and trailing commas; `ConvertTo-Json -Depth 32` writes two-space indentation that matches the template's JSON files, but with CRLF on Windows — replace `"`r`n"` with `"`n"`.
  - A PowerShell function that returns an array unrolls it; return a list with `return ,$array`.
  - Copier prints "Make sure Git >= 2.24 is installed to improve updates." on this PC; it is noise.

## Decisions
- Adoption is a script, `Adopt-Project.ps1`, beside `New-Project.ps1`, backed by `adopt\Adoption.psm1`; only the judgment that remains (folding old instruction files into `AGENTS.md`, reconciling CI) goes to `/plan-migration` in the adopted repository, which the script prints as a ready request.
- Merged files are rebuilt as the template's render followed by the repository's own content, never kept as the repository's file: a kept file makes the repository's diff replace the whole file, so the next template change to it conflicts (tested: keeping `.gitignore` made the next update exit 1; appending merged cleanly).
- Merge strategy by file: `.gitignore`, `.gitattributes`, `.editorconfig` — append the repository's lines verbatim under a comment (`.editorconfig` drops its `root =` lines); `*.json` — merge key by key in the template's key order, the repository's scalar values win, lists are combined (template items first), comments are dropped; `*.props` — append the repository's elements before `</Project>`; anything else, including YAML CI and Dependabot files — keep the repository's file and report that a template change to it will conflict.
- `AGENTS.md` gets the template's index entry under its `## Instructions` heading if it has one, else in a new `## Project Template` section before its first `## ` heading, else at the end. `Directory.Build.props` gets the import of `build/ProjectTemplate.props` as its first element, so its own settings override the template's.
- A .NET repository without `Directory.Packages.props` moves to central package management; when projects disagree on a version, the highest wins and the report says so.
- Answers: `-Data` beats legacy adapters, which beat what the script works out, which beats the template defaults. The script never prompts.
- Legacy setups are an open set: one script per setup in `adopt\legacy\`, with `-Phase Detect|Answers|Apply`; adding a setup is adding a file.
- The script verifies only after adopting (no baseline run): on failure it stages everything, commits nothing and exits 1, like `Update-Project.ps1` on a conflict. It commits on the current branch, like `Update-Project.ps1`.
- `workflow_tools` is a multi-select question with `claude`, `copilot` and `local`, default all three, implemented with templated `_exclude` patterns. NCode.Identity will use `claude, copilot`.
- The Copilot executor prompt is always `execute-step.prompt.md`, matching the `execute-step` skill; the local one is `execute-step-local.prompt.md` when both are installed. NCode.Identity's prompt/skill check requires matching names.
- NuGet packaging is an opt-in `nuget_package` question with a required SPDX `package_license` and an optional `package_icon`; `build/ProjectTemplate.props` then sets the license expression, packs the root `README.md` and the icon, turns on XML documentation, `PublishRepositoryUrl`, `EmbedUntrackedSources` and `snupkg` symbol packages. Source Link is built into the .NET 8+ SDK, so no package reference.
- The scaffold's `GlobalAssemblyInfo.cs` (CLSCompliant and ComVisible false), its copies of `LICENSE.txt` and `COPYRIGHT.txt` in each package, and its build-time release notes are not carried over: the license expression replaces the license file, and the rest is obsolete or non-deterministic.
- Files the script edits are written UTF-8 without BOM with LF endings.
- In the generated folders, ownership is per file: a command, skill or agent a project adds under a new name is the project's.
- Adoption tests are a separate script, `Test-Adoption.ps1`, run as its own CI step, so each stays under two minutes.
- AI agent attribution stays out of commits (added during this run, outside the steps, in its own commit "Keep AI agent attribution out of commits"): `attribution` off in `.claude/settings.json`, `git.addAICoAuthor` off in `.vscode/settings.json`, a rule in the template rules (the bullet starting `- Commits and pull requests record the people`) and in the root `AGENTS.md`, and `template/.githooks/commit-msg`, which `New-Project.ps1` and `Update-Project.ps1` enable with `git config core.hooksPath .githooks` and mark executable. Every step keeps these lines when it edits those files; adopting enables the hook the same way.

- Step 3 (re-plan): the default render of `.vscode/settings.json` must equal the old file byte for byte, apart from the `"git.addAICoAuthor": "off"` line added for commit attribution after step 3; the Done-when checks the literal `\n`, because the template's JSON check parses leniently and accepted a literal line break inside `"\n"`.
- Step 14 (re-plan): the `plain` fixture gets a `pyproject.toml`; Python detection stays as in step 9 (a marker file at the root, not any `*.py`), so a folder of loose scripts is `other`.
- Step 18 (re-plan, before its first run): it also fixes two things found while verifying steps 13–17 — the unit check's `scaffold` folder name collides with the step 16 fixture, and `Test-Adoption.ps1` can end with a non-zero `$LASTEXITCODE` after printing PASSED, which fails a GitHub Actions `pwsh` step.

## Out of scope
- Adopting any real repository — NCode.Identity, the NCodeGroup libraries, identity-platform, the homelab repositories. Each is a separate change once this ships; NCode.Identity's also amends its ADR-0170 and its prompt/skill check.
- The personal-notes repository (`plan-and-execute.md` names `execute-step-copilot`; `configuration-g.md` describes `copier copy` for existing repositories). A follow-up there.
- Versioning or publishing CI for libraries, removing redundant `Microsoft.SourceLink.GitHub` references, and merging a repository's own CI into `ci.yml` — per-repository judgment.
- Tagging or pushing a template release.
- Any change to `Update-Project.ps1` other than formatting list answers in step 7.
- Pester or any new test framework; tests stay plain scripts with `Check`.
- No files other than those each step lists.
