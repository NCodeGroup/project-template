# Project Template

Private [Copier](https://copier.readthedocs.io/) template for new repositories set up for plan-then-execute AI coding: Claude Opus plans each change into `PLAN.md`, a cheaper model executes it one verified step at a time, and any step that needs a decision goes back to Opus. Every project works with Claude Code and with GitHub Copilot, and you can switch between them at any time ([Claude Code or GitHub Copilot](#claude-code-or-github-copilot)). The base works for any language, with the decisions behind its rules recorded as ADRs; a .NET layer adds shared build settings, analyzers, banned APIs, C# and test conventions, and for libraries the license files, icon and a NuGet publish workflow. It serves NCodeGroup's repositories, which are on GitHub, and supports no other host: GitLab isn't supported, and a GitLab template, if one is ever needed, is a separate template there ([ADR-0040](template/docs/decisions/project-template/0040-the-template-serves-ncodegroups-repositories-on-github-only.md)). The GitLab answer, files and passages the template still has, this README's included, are removed by the stories of [#527](https://github.com/NCodeGroup/project-template/issues/527). Every project made from it can pull later template improvements with `Update-Project.ps1`.

**Related:** [Configuration G](https://github.com/polewskm/personal-notes/blob/main/ham-radio/shack/shack-pc/local-ai/configuration-g.md) — the accounts, the shack PC, the VS Code tunnel and the daily loop this template is built for. [Plan-and-execute](https://github.com/polewskm/personal-notes/blob/main/ham-radio/shack/shack-pc/local-ai/plan-and-execute.md) — how the workflow works and how to choose between its variants. This repository is the single source of truth for the workflow's templates and scripts ([workflow/](workflow/)); personal-notes and every project consume them. [USAGE.md](USAGE.md) — setting up a PC for Claude Code and GitHub Copilot, and using and switching between them.

## What a Project Gets

Every file has one of three owners, listed in `copier.yml`:

| Owner | Files | On [update](#update-a-project) |
|---|---|---|
| Template | The workflow machinery | Replaced; an edit in the project is discarded |
| Template and project, merged | Settings files whose tools can't include a second file | The template's changes merge with the project's edits, like a Git merge |
| Project | `AGENTS.md`, `README.md`, `.node-version` (with `uses_node`) and, for .NET, `Directory.Build.props` and, for a library, `version.json` | Never touched |

Where a tool can include a second file, the template's part and the project's part are separate files, so the project changes the template's behavior without editing it ([Extend or Override the Template](#extend-or-override-the-template)).

### Template-Owned Files

Replaced on every update. A project never edits them; an edit is discarded by the next update. A project that has to keep its own version of one, such as a `build/dod.ps1` of its own, names it in the `project_owned_files` answer, which makes it project-owned ([Project-Owned Files](#project-owned-files)).

### Merged Files

The project edits them freely, and later template changes merge in: an update keeps the project's edits and adds the template's, and only the same lines changed on both sides [conflict](#resolve-a-conflict). These are the files whose tools can't include a second file — `_merged_files` in `copier.yml` lists them.

A project that replaced a merged file with its own, such as a CI workflow of its own, makes it project-owned: `.\.template\Update-Project.ps1 -Data @{ project_owned_files = '.github/workflows/ci.yml' }`, or a list of several files. `Adopt-Project.ps1` takes the same answer: `-Data @{ project_owned_files = '.github/workflows/ci.yml' }` keeps the repository's own file exactly as it is. Updates then leave the file alone and show the template's changes to it, as for the project-owned files below. Without the answer, a rewritten file shares almost no lines with the template, so the template's changes conflict in unrelated places. When the template changed a merged file that shares less than half its distinct non-blank lines with the template's version of it, `Update-Project.ps1` names the file and prints the `-Data` to run; it only suggests, and the update goes on. The answer can name a template-owned file too ([Project-Owned Files](#project-owned-files)). `-Data @{ project_owned_files = @() }` gives the files back to the template: merged files merge again, and template-owned ones are replaced again.

### Project-Owned Files

Written once, when the project is created, and never touched by an update, even when the template's copy changes; `Update-Project.ps1` lists those changes. `_skip_if_exists` in `copier.yml` lists these files. So is each file the `project_owned_files` answer names, merged or template-owned. A project that replaced one, such as its CI workflow or a `build/dod.ps1` of its own, sets the answer with `.\.template\Update-Project.ps1 -Data @{ project_owned_files = '.github/workflows/ci.yml', 'build/dod.ps1' }`, naming every file it owns, and `Adopt-Project.ps1` takes the same `-Data`. That update and every later one leave the files alone, never resetting a template-owned one to the template's copy, and show the template's changes to them. When an update stops on a conflict in a template-owned file, such as a `build/dod.ps1` of the project's own that the template now adds, `Update-Project.ps1` names the file and prints that command, with the files the answer already names and any merged file the project seems to have replaced; abandon the update with `git reset --hard; git clean -fd` and run it. The answer can name any file that the version the update moves to renders, also one that version adds or first merges, except the update's own files: `.copier-answers.yml`, `.template-version` and those in `.template/`. Any other name, such as a file that version no longer renders, stops the update before it changes anything ([Merged Files](#merged-files)).

## Claude Code or GitHub Copilot

Every project carries the same workflow for both, so you can work on it with your Claude plan or your Copilot plan, and switch whenever you like: open the other panel in VS Code, or run `claude` or `copilot` in a terminal. Nothing in the project needs to change. `PLAN.md` is the only state the tools share, so one can plan and another execute, re-plan or review. Each plan lives in its own git worktree, `.claude/worktrees/<name>/`, in every tool, so several sessions can work on different plans at once; a Copilot session starts each command in the plan's folder; open that folder to continue the plan in the other tool. A Claude Code cloud session, which may push only to the branch made for it, still makes each plan on its own branch and lands it through that branch, one pull request at a time ([USAGE.md](USAGE.md#work-on-a-project)). Each request bills the plan of the tool that makes it.

[USAGE.md](USAGE.md) is the guide: the tools to install, signing in to each, the commands per tool, switching mid-plan, and troubleshooting.
## Extend or Override the Template

A project never edits a template-owned file. It adds to the template and overrides it with files of its own, which win where they differ.

`AGENTS.md` is the project's index. Its first entry imports the template's rules; every entry after it is the project's:

```markdown
## Instructions

- @.github/instructions/project-template.instructions.md — the plan-then-execute workflow and base conventions, from the project template. …
- @.github/instructions/api.instructions.md — how this project designs its HTTP API
- @docs/agents/releases.md — how to cut a release
```

| To | Add | Picked up by |
|---|---|---|
| Add an instruction, or override one of the template's, for every agent | A line under Conventions in `AGENTS.md`, or a file listed in its index as `@<path> — what it covers`. A `.github/instructions/<name>.instructions.md` file with an `applyTo` glob also reaches Copilot automatically | Claude Code imports each `@` entry; Copilot reads `AGENTS.md` and loads every `.github/instructions/` file; other agents follow the index |
| Add a command, skill or agent | A file with a new name in `.claude/commands/`, `.github/prompts/`, `.github/skills/<name>/` or `.github/agents/` | The tool; updates leave it alone |
| Add an instruction for Claude Code only | `.claude/rules/<name>.md` | Claude Code loads every file there |
| Override a .NET build setting | A property in `Directory.Build.props`, after its import of `build/ProjectTemplate.props` | MSBuild: the later value wins |
| Change a merged file — `.gitignore`, CI, editor settings, permissions | Edit the file; later template changes merge into it | — |

An instruction override is the project's word against the template's, so say it plainly — "Ignore the template's rule on X; here, do Y" — and the agents follow the project.

## Create a Project

[USAGE.md](USAGE.md#install-the-tools) sets all of it up, along with Claude Code and GitHub Copilot.

```powershell
.\New-Project.ps1 -Path C:\src\qso-viewer                                # asks the questions, then git init and the first commit
.\New-Project.ps1 -Path C:\src\qso-viewer -CreateRemote                  # also creates the repository on GitHub, public, and pushes
.\New-Project.ps1 -Path C:\src\qso-viewer -CreateRemote -Visibility private                # the same, but private
.\New-Project.ps1 -Path C:\src\qso-viewer -CreateRemote -Owner bixbots   # under a GitHub organization
.\New-Project.ps1 -Path C:\src\Buffers -CreateRemote -Owner NCodeGroup -Data @{ stack = 'dotnet' }   # a .NET project, NCode.Buffers: named for its root namespace, checked before any question
.\New-Project.ps1 -Path C:\src\qso-viewer -CreateRemote -Defaults -Data @{ project_name = 'QSO Viewer'; stack = 'python' }   # asks nothing: GitHub, public
```

| Parameter | Default | Purpose |
|---|---|---|
| `-Path` | — | New, empty project folder; its name becomes the repository name, so with `-CreateRemote` it follows NCodeGroup's rule ([ADR-0045](template/docs/decisions/project-template/0045-new-project-names-a-repository-by-ncodegroups-rule-and-refuses-a-name-that-doesnt-fit.md)): for `stack` `dotnet`, the root namespace without `NCode.`, such as `Buffers` for `NCode.Buffers`, or `Collections.Providers`; for every other stack, lowercase kebab case, such as `qso-viewer` |
| `-Template` | `https://github.com/NCodeGroup/project-template.git` | Template source; `.` uses this clone, and a clone's `origin` remote becomes the address the project records ([The Template's Address](#the-templates-address)) |
| `-Ref` | The newest tag | Template version to use |
| `-CreateRemote`, `-Owner` | Off, your account | Create the repository on GitHub with `gh repo create`, and push `main` |
| `-NoBaseline` | Off | Skip protecting the new repository with `tools/Set-RepositoryBaseline.ps1` after `-CreateRemote` creates it |
| `-Visibility` | `public` | The new repository's visibility: `public`, `private`, or `internal` (organizations under an enterprise account only) |
| `-Data` | None | Answers given in advance, so those questions aren't asked: `-Data @{ project_name = 'Demo'; stack = 'python' }`. A `git_host` other than `github` stops the script: the template is for NCodeGroup's GitHub repositories only ([ADR-0040](template/docs/decisions/project-template/0040-the-template-serves-ncodegroups-repositories-on-github-only.md)) |
| `-Defaults` | Off | Ask nothing: every question not in `-Data` takes its default |

The script runs `copier copy`, which asks the [questions](#questions) and writes the files and the answers (`.copier-answers.yml`), then `git init -b main`, enables the template's Git hooks (`git config core.hooksPath .githooks`) unless Git already has a hooks path for the new repository, such as a global one, which it keeps and warns about, and makes the first commit, `Create project from project-template v0.1.0`. Copier doesn't ask the `git_host` question: the script answers `github` unless `-Data` names it. With `-CreateRemote` it first checks `<name>`, the folder's name, against the `stack` answer by that rule: a name that doesn't fit stops the script with an error that names the one that fits, deletes the files Copier wrote and creates nothing on GitHub, and with `stack` in `-Data` it stops before Copier asks anything. A name that fits, it runs `gh repo create <name> --public --source . --push`; `-Visibility` replaces `--public` with `--private` or `--internal`. It then runs `tools/Set-RepositoryBaseline.ps1` ([Protect the Default Branch](#protect-the-default-branch)), unless `-NoBaseline` says not to.

A public project is readable by anyone, including its `.copier-answers.yml`, which names this template; the template is public too, so anyone can run `copier update` against it. Secrets stay out of it as in any project (`AGENTS.md`, `.gitignore`), and its CI is safe for pull requests from forks: `pull_request` with a read-only token and no secrets. Its `license` answer, Apache-2.0 unless you answer otherwise, gives it `LICENSE.txt`; without a license file the code is all rights reserved, and `.template\Update-Project.ps1` warns until it has one. To change the visibility later: `gh repo edit --visibility private --accept-visibility-change-consequences`.

For a .NET project, `dotnet new` templates put a `Version` on each `<PackageReference>`, which central package management rejects (NU1008); move each version into `Directory.Packages.props`. The template's rules tell the agents the same, and `dotnet add package` already does it. Add each project to one solution at the repository root (`dotnet new sln` once, then `dotnet sln add <project folder>`), so the default `dotnet build` and `dotnet test` — and CI — cover it.

To bring an existing repository under the template, use [Adopt-Project.ps1](#adopt-an-existing-repository).

## Adopt an Existing Repository

[docs/adopt.md](docs/adopt.md) is the runbook that takes a repository through every manual step in order; this section is the reference for the script. `Adopt-Project.ps1` brings a repository that already exists under the template, so it gets the workflow and later updates. Run it from this clone, on a repository with a clean working tree. It needs the same tools as [Create a Project](#create-a-project).

```powershell
.\Adopt-Project.ps1 -Path C:\src\buffers                                                    # works out the answers, adopts, verifies, commits
.\Adopt-Project.ps1 -Path C:\src\buffers -Data @{ workflow_tools = 'claude', 'copilot', 'local' }    # adds the Hybrid agents, which use the shack PC's private model; without it a repository with no Copilot or Hybrid agent files gets Claude Code and Copilot only
.\Adopt-Project.ps1 -Path C:\src\buffers -Data @{ project_owned_files = '.github/workflows/ci.yml' }  # keeps the repository's own CI workflow as it is, and later updates show the template's changes to it
.\Adopt-Project.ps1 -Path C:\src\buffers -NoCommit                                          # stages the result for review instead
```

| Parameter | Default | Purpose |
|---|---|---|
| `-Path` | — | The repository's root folder |
| `-Template` | `https://github.com/NCodeGroup/project-template.git` | Template source; `.` uses this clone, and a clone's `origin` remote becomes the address the project records ([The Template's Address](#the-templates-address)) |
| `-Ref` | The newest tag | Template version to use |
| `-Data` | None | Answers that win over everything the script works out: `-Data @{ stack = 'node' }` |
| `-NoVerify` | Off | Skip the build and test commands before the commit |
| `-NoCommit` | Off | Stage the result instead of committing it; it still verifies unless `-NoVerify` is also given |

The script refuses a folder that isn't the root of a Git repository, has uncommitted changes, has no commits yet, already has `.copier-answers.yml` (use `Update-Project.ps1` instead), or has no Git `user.name` or `user.email`. It also refuses a repository whose `origin` remote isn't on GitHub, and a `-Data` `git_host` other than `github`, saying the template is for NCodeGroup's GitHub repositories only ([ADR-0040](template/docs/decisions/project-template/0040-the-template-serves-ncodegroups-repositories-on-github-only.md)).

### How it works

It never asks a question. Each answer comes from the first of these that has it:

1. `-Data`.
2. A [legacy adapter](#legacy-adapters).
3. What the script works out from the repository.
4. The template's default.

The script works out these answers:

| Answer | Worked out from |
|---|---|
| `stack` | `dotnet` if there is a solution or a C#, F# or VB project within two folders of the root; else `node` if `package.json` is at the root; else `python` if `pyproject.toml`, `requirements.txt` or `setup.py` is; else `other` if there is an OpenTofu or Terraform file (`.tf`, `.tofu` or `.tftest.hcl`) within two folders of the root; else `powershell` if there is a `.ps1`, `.psm1` or `.psd1` file outside the `build`, `eng`, `scripts`, `tools` and `.github` folders at the root; else `other` |
| `project_name` | The only solution's name, else the `origin` remote's repository name, else the main checkout's folder name, so a Claude Code worktree doesn't name the project after itself |
| `git_host` | Always `github`: the script refuses a repository whose `origin` remote isn't on GitHub |
| `author_name` (.NET) | `Authors`, else `Company`, in the root `Directory.Build.props` |
| `license` | `PackageLicenseExpression` in the root `Directory.Build.props` (.NET); else `Apache-2.0` or `MIT` when the root `LICENSE`, `LICENSE.txt`, `LICENSE.md` or `COPYING` holds that license's text; else blank, never the template's `Apache-2.0` default, and the adoption warns when the repository has no license file ([ADR-0024](template/docs/decisions/project-template/0024-a-project-is-licensed-under-apache-2-0-unless-it-answers-otherwise.md)) |
| `build_command`, `test_command` (.NET) | `dotnet build <solution>` and `dotnet test <solution>`, when the only solution isn't at the root |
| `package_manager` (Node.js) | The one the `packageManager` field in `package.json` names, else the one whose lockfile is at the root (`pnpm-lock.yaml`, `yarn.lock`, `bun.lock` or `bun.lockb`), else npm |
| `uses_node` (not Node.js) | Yes when a `package.json` is within two folders of the root, outside `bin`, `obj`, `node_modules`, `.git` and `.claude`, or a `.nvmrc` or `.node-version` is at the root; a Node.js repository takes the default, yes |
| `build_command`, `test_command` (Node.js) | `<package_manager> run build` and `<package_manager> run test`, each only when `package.json` has that script and the `test` script isn't the failing placeholder `npm init` writes; else blank |
| `workflow_tools` | `claude`, plus `copilot` if `.github/agents/copilot-*.agent.md`, `.github/skills/` or `.github/prompts/` exists, plus `local` if `.github/agents/hybrid-*.agent.md` exists; with none of these, the template's default (`claude` and `copilot`), and the script prints a line saying so and how to add `local` |

Everything else takes the template's default. The script prints the answers, runs `copier copy --overwrite`, and enables the template's Git hooks (`git config core.hooksPath .githooks`) unless the repository already sets its own, has hooks in `.git/hooks`, which a hooks path would turn off, or uses pre-commit, which won't install while a hooks path is set; then it warns, naming the command that runs them.

What it does with a file the repository already has depends on the file's owner ([What a Project Gets](#what-a-project-gets)):

| Owner | What happens |
|---|---|
| Template | Replaced by the template's file; the repository's copy is discarded, unless the `project_owned_files` answer names it: then the repository's copy is kept exactly as it is, and later updates show the template's changes to it |
| Merged | Rebuilt as the template's file plus the repository's own content, so a later update merges the repository's content like any project's edits (below) |
| Project | Kept. `AGENTS.md` gains the template's rules as an index entry: first under its `## Instructions` heading, else in a new `## Project Template` section before its first section, else at the end. `Directory.Build.props` gains the import of `build/ProjectTemplate.props` as its first element, so its own settings override the template's. An `AGENTS.md` the template writes, for a repository that had none, says `pre-release: tracked` in its Landing section, since the repository has a history (ADR-0015). A `.node-version` the repository has is kept; with only a `.nvmrc` that names a version number, such as `v22`, `.node-version` gets that version, and any other `.nvmrc` value is a follow-up. |

A merged file is rebuilt by type:

| File | Rebuilt as |
|---|---|
| A file the `project_owned_files` answer names, such as `-Data @{ project_owned_files = '.github/workflows/ci.yml' }` | The repository's file, exactly as it is; Copier doesn't touch it, and a file the repository lacks isn't created. Later updates leave it alone and show the template's changes to it ([Merged Files](#merged-files)). A template-owned file can be named too; a file the template doesn't render, or one of the update's own files (`.copier-answers.yml`, `.template-version`, `.template/`), stops the adoption before it changes anything |
| `.gitignore`, `.gitattributes`, `.editorconfig` | The template's file, then the repository's lines under a comment (`.editorconfig` drops its `root =` lines; `.gitattributes` drops a catch-all text rule such as `* text eol=lf`, because Git uses the last rule that matches and the repository's lines come after the template's, so it would override the template's binary rules and corrupt an image). An update sets those lines aside while Copier merges and puts them back at the end, so a template change never conflicts with them |
| `*.json` | The two merged key by key in the template's order; the repository's values win and lists are combined. Comments are dropped, and the report says so. The exception is `global.json` with a partial SDK version, such as `10.0.0`, and a `rollForward` policy: the template's CI reads it with `actions/setup-dotnet` on GitHub and `build/Install-Dotnet.ps1` on GitLab, which both reject that, so the template's file is used and the report says so |
| `*.props` | The template's file with the repository's elements added before `</Project>` |
| Anything else, such as YAML CI and Dependabot files | The repository's file, kept. A template change to it conflicts on update: keep your side; or name it in `project_owned_files` when adopting |

A .NET repository without `Directory.Packages.props` moves to central package management: each `Version` goes from the project files into `Directory.Packages.props`. When projects disagree on a version, the highest wins and the report says so.

Before committing, the script runs the build and test commands from the answers. It then commits on the current branch as `Adopt project-template v0.1.0`, with the report of what it merged, removed and moved as the message body. If a command fails, it stages everything, commits nothing, and exits 1; fix the problem and commit, or abandon the adoption with `git reset --hard; git clean -fd`. If anything else fails after the template is applied, the script resets the repository to where it was and says so, so there is nothing to clean up.

Some judgment is left to you. The script prints it as a ready request: folding `.github/copilot-instructions.md` into `AGENTS.md`; for a .NET repository, reconciling the template's `csharp.instructions.md` with the repository's own instruction files; and, when the template added `ci.yml` because the repository had none, reconciling its other workflows in `.github/workflows` with it. A `ci.yml` the repository already had is kept, and so is every workflow beside it. On GitHub, the adoption then prints, word for word, the notes `Update-Project.ps1` prints when that `ci.yml` has no `workflow_call` trigger, or asks for more than `contents: read` in its top-level `permissions:` or a job's: `tag-release.yml` calls it with only `contents: read` before it tags a release, so until it is fixed, no release is tagged.

When the repository has version tags merged into the current branch that its changelog has no section for, the request also says to backfill them, such as `backfill CHANGELOG.md from the releases v0.1.0..v0.3.0`. The changelog is the file the `changelog` key of `AGENTS.md`'s Landing section names, `CHANGELOG.md` by default, and only tags shaped like `v1.2.3` or `1.2.3` count. With `pre-release: untracked` in that Landing section, the tags below 1.0.0 don't count.

For a .NET library, adoption sets the `version.json` it adds to the patch after the newest release tag, with the `assemblyVersion` a release of its current major shipped when it was built with a higher one than the template pins, such as `{ "version": "5.3", "precision": "minor" }`, and the request asks to add `-p:PublicRelease=true` to a `publish.yml` the repository keeps without it. A library whose own workflow already runs `nuget push` keeps it alone, without the template's `publish.yml`, `release-provenance.yml` or `raise-baseline.yml`, records it in the `nuget_publisher` answer, and the report says so. Adoption drops the repository's own Nerdbank.GitVersioning reference, which `build/ProjectTemplate.props` makes a second one once `version.json` exists, and reports it; the update warns about a `.gitlab-ci.yml` that packs without `PublicRelease=true` or `GIT_DEPTH: "0"`, as it does for a `publish.yml`, and both name each job of the repository's own workflows that builds in a checkout without `fetch-depth: 0` or passes `-p:Version`, leaving out a checkout no build step's working directory lies in. Adoption and the update both name the stale NuGet logistics of an older library (an unimported `.props` file, `GeneratePackageOnBuild`, settings the template already makes, a `.sln`, a UTF-8 BOM, projects at the root) and fix none (ADR-0149). They also compare each packable project's Description and PackageTags with the newest published package and name any that differ. A repository that keeps its own `.github/workflows/publish.yml` without a `workflow_dispatch` trigger gets the warning `Update-Project.ps1` prints for it: the Release workflow, `tag-release.yml`, starts `publish.yml` through that trigger, so until it has one, a release ships no packages. With `release: tag+release` in the `AGENTS.md` adoption leaves, a library whose `nuget_publisher` workflows have no `workflow_dispatch` trigger gets the note the update prints for each, and both recognize the trigger in a block or a flow sequence, such as `on: [release, workflow_dispatch]`. A .NET library on GitHub whose kept `AGENTS.md` says `release: none` or `tag`, or has no release line, gets the note the update prints with the one-line change to `- release: tag+release`, unless the repository has no `.github/workflows/tag-release.yml` or a `nuget_publisher` workflow has no `workflow_dispatch` trigger or doesn't exist.

```text
Still to do — in the repository, run:
  /plan-migration Finish adopting the project template: fold .github/copilot-instructions.md into AGENTS.md or a file it lists; reconcile .github/workflows/main.yml with ci.yml
```

Afterwards the repository updates like any project: `.\.template\Update-Project.ps1` ([Update a Project](#update-a-project)).

## Protect the Default Branch

[docs/adopt.md](docs/adopt.md#2-protect-the-default-branch-and-tags) says when to run the baseline and how to check it; this section is the reference. A repository on GitHub should take changes only through pull requests, whatever its CI is. `tools/Set-RepositoryBaseline.ps1` gives a repository a "Protect main" ruleset on its default branch, the same shape as this repository's: no deletion, no force push, a pull request required with every conversation resolved (a finding from the review bot, CodeQL or a person blocks the merge until it is resolved), merge-commit or rebase merges only (never squash, so each commit of a plan stays on the branch, as a project's ADR-0013 records; a project that squash-merges, such as through a merge queue, supersedes that one record), where CodeQL's default setup is configured and analyzes at least one language, a code-scanning rule that blocks a pull request whose CodeQL results add an alert at warning level or above or a security alert of any severity, no bypass; the ruleset also dismisses stale approvals on a push, which an earlier run's "Protect main" ruleset gets on the next run, like conversation resolution, and a ruleset of the owner's keeps its shape. It requires no approval, except where NCode Review's approver is set up, or the default branch's `.github/workflows/code-review.yml` passes `approve: true` and a second person has write access: there one approval, of the last push ([ADR-0022](template/docs/decisions/project-template/0022-ncode-reviews-approval-gates-the-merge.md.jinja)). Where one person has write access, counted as the users the repository's collaborators list gives with push access or more, and NCode Review's approver isn't set up, it requires no approval and no approval of the last push, even with `approve: true`, and turns both off in a "Protect main" that requires an approval, saying so, also with `-WhatIf`: GitHub counts toward a required approval only a review from someone with write access, never the author's, and NCode Review's app has none, so on NCodeGroup/PropertyBag#53 its approval left "Approvals, 1 still required" ([ADR-0034](template/docs/decisions/project-template/0034-with-one-writer-the-baseline-requires-no-approval.md)). NCode Review's approver is set up where `code-review.yml` passes `approve: true` and `approver-private-key`, and the repository's `code-review` environment holds `NCODE_REVIEW_APPROVER_PRIVATE_KEY`: the NCode Review Approver, an app that can write, submits the approval with a token that can only write pull requests, so the ruleset requires one approval, of the last push, with one writer too; with the input but no secret, the run names `tools/Enable-CodeReview.ps1 -ApproverPrivateKeyPath` from NCodeGroup/code-review and requires no approval for it ([ADR-0036](template/docs/decisions/project-template/0036-a-required-approval-is-met-by-ncode-reviews-approver-app.md)). A collaborators list it can't read is named, and the ruleset then gets no approval it doesn't have and keeps those it has. A ruleset of the owner's that requires an approval keeps its shape, and with one writer the run prints a notice with the command that requires no approval and no approval of the last push in it, as it does when GitHub refuses the change to "Protect main". It never requires approval of the last push without an approval: GitHub then waits for an approval from someone other than the pusher and never lets an author approve their own pull request, so every merge stays blocked where one maintainer authors every pull request, as it did NCodeGroup/docs on 2026-11-16. A "Protect main" ruleset that has it on with no approval required, which an older run or a hand-made ruleset of that name can, gets it turned off, and the run says so, also with `-WhatIf` ([ADR-0031](template/docs/decisions/project-template/0031-the-baseline-turns-off-approval-of-the-last-push-where-no-approval-is-required.md.jinja)); one that requires approvals keeps it. For a ruleset of the owner's that has it on with no approval, and for "Protect main" where GitHub refuses the change, it prints the `gh api` command that turns it off, and `-All -WhatIf` lists them; `-RequireChecks` adds the CI jobs a pull request must pass as required status checks, on a branch that is up to date with the default branch. Where it reads CodeQL's default setup as configured with a language to analyze, it switches the setup to the extended query suite, before it writes the ruleset, so a refused switch changes nothing and the next run retries it. GitHub can report a default setup as configured with no language: on 2026-11-16 NCodeGroup/docs and NCodeGroup/brand answered `"state":"configured","languages":[]`, their organization's enforced security configuration having turned default setup on before any CodeQL setup ran there, so CodeQL ran on no pull request and the rule blocked every one, with every check green. The script counts such a setup as not configured: it leaves the rule out, says why, and switches no suite, since the switch sends `query_suite` alone and sets up no language; a later run with `-RequireChecks` adds the rule once the repository's settings give CodeQL a language ([ADR-0030](template/docs/decisions/project-template/0030-the-code-scanning-rule-is-added-only-where-codeql-analyzes-a-language.md)). A "Protect main" ruleset that already has a code-scanning rule, such as one an older version of the script made, keeps that rule and its alert thresholds, and the script never switches that repository's suite, since the extended suite can raise new alerts the rule would then block merges on: it reads the default setup and, when it runs another suite, prints a notice with the `gh api` command that switches it by hand. Where the setup is configured but analyzes no language and the rule requires CodeQL, it warns instead that every pull request stays blocked, and names the fix: set up CodeQL's languages in the repository's settings (Settings > Advanced Security > CodeQL analysis), or remove the rule, which the script never does. It prints the notice or the warning also for a "Protect main" that sits beside a ruleset of the owner's. A default-branch ruleset that already requires pull requests, its own or one someone else shaped, keeps its shape, but the script turns on its conversation resolution where it is off, changing nothing else in it, so every repository blocks a merge until each discussion is resolved, as a project's ADR-0014 records. It also turns on delete-branch-on-merge.

It gives the repository a "Protect release tags" ruleset too, on the tags matching `v*`: no deletion and no update, so a release tag is never moved, with no bypass. A release tag names one published package set, so it never changes; creating one stays open, so the Tag and publish release workflow's `GITHUB_TOKEN` can tag a release as its pull request merges, and `/ship-plan` can when that workflow didn't. A ruleset of that name is left alone whatever its state, and so is an active tag ruleset on `v*` tags, or on every tag, that already refuses both deletion and update.

It then turns on the security settings a public project should have, each where it is off: the workflow token (`GITHUB_TOKEN`) read-only by default, with GitHub Actions not allowed to create or approve pull requests, in every repository, since any workflow's approval would count toward a required approval, and `raise-baseline.yml` opens no pull request itself (ADR-0036); `-OrganizationPolicy` sets the organization's defaults the same way; the approval policy for workflows from fork pull requests, raised from `first_time_contributors` to `first_time_contributors_new_to_github` so only an account new to GitHub waits for a maintainer's approval, which `-OrganizationPolicy` raises for the organization too, leaving the stricter `all_external_contributors` and a policy it doesn't know as they are; it checks no runner or workflow, so where it raises the policy it prints a notice that a repository with a self-hosted runner or a `pull_request` workflow that uses secrets must keep `all_external_contributors` ([ADR-0039](template/docs/decisions/project-template/0039-fork-pull-request-workflows-run-for-established-contributors.md)); secret scanning and its push protection; Dependabot alerts and Dependabot security updates, which need the alerts; private vulnerability reporting; and immutable releases, after which GitHub signs an attestation of each release it publishes, which `gh release verify` checks, except where a `.yml` or `.yaml` file in the default branch's `.github/workflows` runs on a `release` event or uploads release assets (`gh release upload`, `actions/upload-release-asset`, `softprops/action-gh-release` or `uploadReleaseAsset`), such as `release-provenance.yml`, which attaches a library's packages to its release, or a project's own workflow that attaches files, since an immutable release refuses a file attached after it is published, or where it can't read one, and with `-SkipImmutableReleases`; the line names the files, and `.template/Update-Project.ps1` then says to delete `SECURITY.md`'s "Releases are immutable" paragraph (`Adopt-Project.ps1` prints the same note); where they are already on and such a workflow exists, it prints a notice with the `gh api -X DELETE` command that turns them off, since it never loosens a setting ([ADR-0028](template/docs/decisions/project-template/0028-github-releases-are-immutable-and-their-tags-signed.md)). Each is read first and reported as set, already set, would set (with `-WhatIf`) or not available, with the reason, and none costs money: secret scanning and its push protection are left out of a repository that isn't public, where they need the paid GitHub Secret Protection. A setting the API won't read or refuses to change, such as private vulnerability reporting on a private repository, or a token setting the organization decides, is reported, and the run goes on with the next one. Requiring actions to be pinned to a full-length commit SHA is left out: it fails every workflow that names an action by tag, which an adopted repository's workflows may.

Last, it allows auto-merge where it is off, read and reported the same way, so `.github/workflows/code-review-auto-merge.yml` can have a Dependabot bump of NCode Review merge itself ([Stay Current](#stay-current)). Allowing it merges nothing by itself: a pull request merges itself only once someone, or that workflow, turns auto-merge on, and still waits for what the ruleset requires and merges only as it allows.

For a public repository with one writer, the run ends with a notice naming `tools/Dismiss-ScorecardAlerts.ps1`. One person can't bring Scorecard's Branch-Protection, CII-Best-Practices and Contributors checks to 10, so their code scanning alerts never close; `.\tools\Dismiss-ScorecardAlerts.ps1 -Repo <owner>/<name> -WhatIf` lists every open Scorecard alert and the ones it would dismiss as won't fix, with a standard comment: the one [ADR-0035](template/docs/decisions/project-template/0035-a-sole-maintainer-dismisses-the-scorecard-alerts-one-person-cannot-clear.md) gives for CII-Best-Practices and Contributors, and for Branch-Protection one that cites [ADR-0034](template/docs/decisions/project-template/0034-with-one-writer-the-baseline-requires-no-approval.md) and [ADR-0036](template/docs/decisions/project-template/0036-a-required-approval-is-met-by-ncode-reviews-approver-app.md), since the one ADR-0035 gives predates ADR-0036. It leaves every other alert open; without `-WhatIf` it dismisses them. With two writers or more it dismisses nothing.

From December 2, 2026, GitHub blocks workflows that start on `pull_request_target` in a public repository that has no Actions event policy allowing the event, and not in a private or internal one ([Default policy for `pull_request_target`](https://gh.io/securely-using-pull_request_target#default-policy-for-pull_request_target)); brownouts before then already block it. The template's two workflows keep the event: `code-review.yml` runs from the default branch so a pull request can't change its own review, and its `code-review` environment, which Anthropic's federation rule trusts, accepts only default-branch runs; `code-review-auto-merge.yml` needs `contents: write` and `pull-requests: write` on a Dependabot pull request, which `pull_request` doesn't grant; neither checks out or runs the pull request's code. So for a public repository that has either file on its default branch, the script creates the active policy "Allow pull_request_target for code review" for those two files alone, allowing `pull_request_target` and `issue_comment`, the events the template's two files start on, and every other event either file's top-level `on:` key names, such as a `workflow_dispatch` a project adds to its `code-review.yml`; an event rule allows only the events it lists, for the workflows it targets, so every other workflow keeps GitHub's default. It reads `on:` as one event, a list in brackets, the keys or items indented below it, or `- ` items at its own indent; a mapping in braces adds no event. It leaves alone a repository that isn't public or has neither file, and an active policy, the repository's or, when the account running it may read them, its organization's, that already allows each of those events for its files. A policy of that name is updated in place when it isn't active, doesn't allow an event the files start on or doesn't cover both files: the script sends the whole policy again, keeping any other event it allows, and says what was wrong, also when the update is refused, so a project that adds a trigger to its `code-review.yml` reruns the script. When the organization's policies can't be read for a reason other than HTTP 403 or 404, which an account that may not read them, or a user's repository, gets, the policy's line says so. Outcomes are reported like a security setting's and a refusal doesn't fail the run. GitHub stores the repository policy as the script sends it, on every plan, GitHub Free included: read back with `gh api repos/<owner>/<name>/actions/policies/<id>`, it is active, names the two workflow files under `conditions.workflow_path`, and has one `restrict_action_events` rule allowing `pull_request_target` and `issue_comment`.

An organization owner can instead run it once with `-OrganizationPolicy`, which creates the same policy for the organization, on every repository, and touches no repository. It needs GitHub Team or above, since GitHub offers organization event policies only on those plans, and the `admin:org` scope. On another plan, such as GitHub Free, where GitHub answers `Upgrade to GitHub Team to enable this feature.`, it says so and to run the script for each repository instead, with `-Repo <name>`, or with `-All` once its `-WhatIf` looks right: a repository's own policy works on every plan. It updates one of that name in place, keeping the other events it allows, when it isn't active, misses one of those events or doesn't cover both files on every repository, and leaves alone one that does, or an active one that already allows `pull_request_target` and `issue_comment` for both files on every repository, `-WhatIf` prints the body, and it exits 1 when it can't read the policies or is refused, or when the organization's workflow token setting or fork pull request approval policy fails; a later repository run finds it, when its account may read the organization's policies, and adds none.

```powershell
gh auth refresh -h github.com -s admin:org
.\tools\Set-RepositoryBaseline.ps1 -OrganizationPolicy -Owner NCodeGroup -WhatIf   # prints the policy it would post
.\tools\Set-RepositoryBaseline.ps1 -OrganizationPolicy -Owner NCodeGroup
```

- **A new repository:** `New-Project.ps1 -CreateRemote` runs it for a GitHub repository after the first push, requiring the template's `build-and-test` job. `-NoBaseline` skips it. If it fails, the repository exists and the script says how to run it again. It can leave the code-scanning rule out: where an organization's security configuration turns CodeQL's default setup on, the setup may analyze no language yet right after the first push, as on NCodeGroup/docs and NCodeGroup/brand, and the run says so. Once CodeQL's languages are set up in the repository's settings, run the baseline again with `-RequireChecks build-and-test` to add the rule ([ADR-0030](template/docs/decisions/project-template/0030-the-code-scanning-rule-is-added-only-where-codeql-analyzes-a-language.md)).
- **An adopted repository:** `Adopt-Project.ps1` only commits locally, so it prints the command to run, with the same `-RequireChecks` when the repository's CI is the template's and, when it isn't, a reminder to pass `-RequireChecks auto` or name its own jobs.
- **A repository that is protected already** (an active ruleset on the default branch that requires pull requests) keeps that ruleset, and so does one with the "Protect main" ruleset an earlier run made; both still get the release tags ruleset, the security settings, auto-merge and the event policy, so running the script again brings a repository protected by an older version up to date. `-WhatIf` shows what the script would do, and `-All -Owner <owner>` covers every repository an owner has, except archived repositories and forks. A repository the script skips for its default branch, because CodeQL's default setup can't be read or `-RequireChecks auto` finds nothing to require, gets nothing else either. GitHub Free has no organization rulesets, so this applies them to each repository.
- Name only jobs that run on pull requests with `-RequireChecks`: a job that runs on a release or a schedule never reports on a pull request, and requiring it would block every merge.
- **`-RequireChecks auto`** names them for you. It reads the check runs on the head commit of the latest pull request merged into the default branch, which it finds among every closed pull request, and requires the GitHub Actions jobs that ran there for the `pull_request` event and passed. It leaves out, with the reason, the review bot's advisory `Code review`, which the person who merges waits for instead ([ADR-0019](template/docs/decisions/project-template/0019-nothing-requires-the-code-review-check-the-person-who-merges-waits-for-it.md.jinja)), and its `pull_request_target` job, `CodeQL` (the code-scanning rule covers it) and its Analyze jobs, checks other apps report, and anything skipped, neutral, failed or unfinished, since a skipped required check counts as passing. A repository with no merged pull request, or no check to require, is skipped with the reason and nothing changes. With `-WhatIf` it lists the checks and prints the command that names them, to trim and run (a job whose name has a comma is listed apart, since `-RequireChecks` would split it); `-All -RequireChecks auto` reads each repository's own pull request. The list comes from one pull request, and every run says so: a job whose workflow has `paths` or `branches` filters reports nothing on a pull request the filters skip, and that pull request can't merge, so run `-WhatIf` first and leave such jobs out.

## Update a Project

Every project carries its update script as `.template\Update-Project.ps1`. Run it in the project:

```powershell
cd C:\src\qso-viewer
.\.template\Update-Project.ps1                # newest template tag; commits the update
.\.template\Update-Project.ps1 -NoCommit      # stages it for review instead
.\.template\Update-Project.ps1 -Ref v0.3.0    # a specific template version
```

From this repository's clone, `.\Update-Project.ps1 -Path C:\src\qso-viewer` does the same: it's a wrapper that runs `template\.template\Update-Project.ps1`, the script's single source.

| Parameter | Default | Purpose |
|---|---|---|
| `-Path` | The project the script sits in | The project; it must have no uncommitted changes |
| `-Ref` | The newest tag | Template version to update to |
| `-Data` | None | Answers to change: `-Data @{ author_name = 'K0MTP' }`. Template-owned and merged files follow the new answer; project-owned files don't |
| `-NoCommit` | Off | Stage the update instead of committing it |
| `-TemplateClone` | None: the script clones the template | A clone of the template to read instead of cloning one; when `_src_path` names a folder that isn't on this PC, its `origin` remote becomes the project's template address ([The Template's Address](#the-templates-address)) |

The script needs no template clone: it clones the template from the address in `.copier-answers.yml` into a temporary folder, with the Git access Copier needs anyway, and deletes it afterwards. The script is template-owned, so it updates itself: when the target version's copy differs from the running one, it hands the update over to that copy, and the newest update logic always does the update. Every version accepts the same parameters, so any version can hand over to any later one. It refuses to run on the default branch (the branch `origin/HEAD` names), because it commits: run it on a branch of its own, such as `git switch -c build/project-template-v0.2.0`, or pass `-NoCommit`.

A project on v0.8.0 or earlier doesn't hand over: its script can't read the newer copy from a template cloned over a URL, so it runs its own, older logic — it prints Copier's raw "Make sure Git >= 2.24 is installed" warning and no "Handing the update over" line — and installs the newer script for the next update ([CHANGELOG.md](CHANGELOG.md#090---2026-10-25)). To run the newest logic on that first update, run the wrapper from a clone of this repository: `git clone https://github.com/polewskm/project-template.git`, then `.\Update-Project.ps1 -Path <project>` in that clone.

On Windows, a project on v0.69.0 to v0.75.0 can't update: the update starts with `copier recopy` at the project's own version, and Git for Windows refuses to check those versions out, because their `uses_node` file names hold a `|`. The script stops before it changes anything when the project's version has a path Git for Windows refuses, names the path, and says to update once from Linux, macOS or WSL, such as with `pwsh ./.template/Update-Project.ps1` in WSL; later updates run on Windows again.

| File | On update |
|---|---|
| Template-owned | Replaced by the new version; files the template added are created, and files it removed are deleted. A local edit is discarded and a deleted file restored, and the script lists both, so the change can move into a project file; a file the update leaves as the project had it, such as an edit the new version also makes or a deleted file it also deletes, is listed under neither, and an edited file is left out of the discarded edits when the update keeps every line the edit changed, such as a pin bump the new version also makes beside changes of its own. An action pin, a `uses: <action>@<sha> # <version>` line, that the project moved past the new version's pin of that action in the same file, such as a Dependabot bump the template hasn't made yet, is kept and listed under Kept, so an update never downgrades it; a pin the new version moves as far or further replaces it. A template-owned file that an earlier template version never updated, such as `docs/decisions/project-template/README.md` before 0.59.1, is first reset to the project's version, discarding a local edit, and listed under Refreshed |
| Merged | The template's changes since the project's version merge with the project's edits. Only the same lines changed on both sides conflict. A merged file the project deleted stays deleted. An adopted project's `.gitattributes` loses a catch-all text rule, such as `* text eol=lf`, from the lines it kept at adoption, and the script says so: those lines come after the template's, and Git uses the last rule that matches, so the rule overrode the template's binary rules. A merged file the project seems to have replaced, sharing less than half its lines with the template's, gets a suggestion to make it project-owned. |
| Project-owned | Including each file, merged or template-owned, that the `project_owned_files` answer names. Never touched, even if the project deleted it. When the template changed one since the project's version, the script shows the template's change, rendered with the project's answers, with `pre-release: untracked` only when `AGENTS.md`'s Landing section says so and with that section's `release` line, leaving out what the project's file already has; copy over what you want |
| `.copier-answers.yml`, `.template-version` | Record the new version |

It stages only what the update changed, the tracked files with `git add -u` and each file it added by name, never with `git add -A`, and from its reset to its end `.git/info/exclude` holds a copy of the project's whole `.gitignore`, an adopted project's kept lines included, so a folder the project ignores, such as `node_modules/` in a checkout with a frontend installed, is never staged, also when the updated `.gitignore` doesn't ignore it. `copier check-update`, run in a project, tells whether a newer template version exists.

With NCode Review, when `.github/workflows/code-review.yml` pins `NCodeGroup/code-review` before v1.5.0, passes no `approve: true` or passes it without `approver-private-key`, or `AGENTS.md`'s Landing section doesn't say `draft: yes`, the update says what to change, also when the project is already up to date, to store the approver's key with NCodeGroup/code-review's `tools/Enable-CodeReview.ps1 -ApproverPrivateKeyPath`, and to run `tools/Set-RepositoryBaseline.ps1` again, so the default branch requires one approval, of the last push, once NCode Review's approver is set up or a second person has write access, and none with one writer otherwise, since GitHub counts no approval from NCode Review's own app ([ADR-0022](template/docs/decisions/project-template/0022-ncode-reviews-approval-gates-the-merge.md.jinja), [ADR-0034](template/docs/decisions/project-template/0034-with-one-writer-the-baseline-requires-no-approval.md), [ADR-0036](template/docs/decisions/project-template/0036-a-required-approval-is-met-by-ncode-reviews-approver-app.md)). Both files are the project's, so the update changes neither.

When the project has version tags merged into the current branch that its changelog has no section for, such as releases from before it had a changelog, the update ends with a request to backfill them:


### The Update Notice

A GitHub project gets `.github/workflows/template-update.yml`, which runs `.template/Get-TemplateUpdate.ps1` every Monday at 07:00 UTC, and on demand from the Actions tab or with `gh workflow run template-update.yml`. It needs only the workflow's own `GITHUB_TOKEN`, with `contents: read` and `issues: write`. The script reads the project's version from `.template-version`, lists the template's tags at `_src_path` in `.copier-answers.yml` with `git ls-remote`, and takes the newest `vX.Y.Z`, as `Update-Project.ps1` does. While the project is behind, it keeps one open issue labeled `template-update` (it creates the label the first time): it opens "Update to project-template v0.42.0" with the `CHANGELOG.md` sections after the project's version up to that tag, read at that tag; a later run edits that same issue, retitling it and rewriting its text when a newer version comes out, and leaves it alone when nothing changed. A section that doesn't fit in an issue is left out, with a link to the changelog. Once the project is on the newest version, the next run closes the open issue with a comment; with no open issue it does nothing. `/plan-issue` on that issue plans the update with `/plan-template-update`'s instructions, so `/triage-issues` and `/run-issues` send it there too. The script rewrites the issue's text, so put notes in comments. To stop the notices, disable the workflow: `gh workflow disable template-update.yml`. The file is template-owned, so deleting or editing it lasts only until the next update. A template that the workflow's token can't read, such as a private one, fails the run.

### The Template's Address

A project records where its template came from in `.copier-answers.yml` (`_src_path`). The template moved from `polewskm/project-template` to `NCodeGroup/project-template`. GitHub redirects the old address, but only while nobody creates a repository at it, so the update script moves a project over: when `_src_path` is `https://github.com/polewskm/project-template.git`, it changes that one line to `https://github.com/NCodeGroup/project-template.git`, clones from there, and commits the change with the update, even when the project is already at the newest version. A project on an older script gets this with the update that hands over to the newer one ([Update a Project](#update-a-project)).

A project created or adopted from a local clone of the template, with `-Template .` or a clone's folder, records the clone's `origin` remote, such as `https://github.com/NCodeGroup/project-template.git`, rather than the folder, which no other PC has, leaving out a user name or token and recording an SSH address on github.com or gitlab.com as its `https://` address, which CI and every PC can read; a clone without an `origin` address leaves the folder, and `New-Project.ps1` and `Adopt-Project.ps1` warn. When `_src_path` names a folder that isn't on the PC the update runs on, the update moves the project to the template's address: the `origin` remote of `-TemplateClone`, a clone of the template to read instead of cloning one, when that is an address, or else `https://github.com/NCodeGroup/project-template.git`, and commits that line with the update. The update notice reads such a project's template at `https://github.com/NCodeGroup/project-template.git`. A project whose own `Update-Project.ps1` is older fails to clone that folder: run `.\.template\Update-Project.ps1 -TemplateClone <a clone of the template>`, which hands the update over to the newer script.

### Resolve a Conflict

When the template and the project changed the same lines of a merged file, the script commits nothing, exits 1, and says how to finish:

```text
Template v0.2.0 -> v0.3.0:
  conflict  .gitignore
  modified  .template-version
  modified  CLAUDE.md

1 file(s) conflict: the template and this project changed the same lines. In each, keep the right lines and delete the <<<<<<<, ======= and >>>>>>> marker lines. Then:
  git add -u
  git diff --cached --check     # prints any marker you missed
  git commit -m "Update from project-template v0.3.0"
To abandon the update instead: git reset --hard; git clean -fd
```

The rest of the update is already in place and staged, deletions included; only the conflicting lines wait for you, so once you resolve them, `git add -u` stages the whole update. In the file, the top half is the project's version and the bottom half the template's:

```text
<<<<<<< before updating
Thumbs.db # project
=======
Thumbs.db # template
>>>>>>> after updating
```

VS Code lists the file under Merge Changes in Source Control and calls the halves Current and Incoming, with Accept buttons above each block. Git won't commit while a file is still unmerged, but `git add` marks it resolved even with markers left in it, so run `git diff --cached --check` before committing.

A conflict in a template-owned file comes from a copy of the project's own, such as a `build/dod.ps1` the template now adds. The script then also names the file and prints the `.\.template\Update-Project.ps1 -Data @{ project_owned_files = ... }` that makes it project-owned, so the project keeps its copy: abandon the update and run that instead ([Project-Owned Files](#project-owned-files)).

## Commit Attribution

A commit records the people who wrote it. AI tools add their own attribution by default — Claude Code a `Co-Authored-By: Claude <noreply@anthropic.com>` trailer and a `Claude-Session:` trailer, Copilot a `Co-authored-by: Copilot` trailer, and Codex, Cursor, Devin, Jules, Gemini, Grok, GitLab Duo, aider and other agents their own trailers, footers, session links or bot accounts — and GitHub then lists the agent as a contributor, which only rewriting published history undoes. Every project, and this repository, prevents it at the source, in settings and rules that travel with the repository, and enforces nothing ([ADR-0018](template/docs/decisions/project-template/0018-agent-attribution-is-avoided-not-enforced.md)):

| Layer | Stops |
|---|---|
| `attribution` in `.claude/settings.json`: `commit` and `pr` empty, `sessionUrl` off | Claude Code's trailers and pull request text |
| `git.addAICoAuthor` off in `.vscode/settings.json` | VS Code's own Copilot trailer when you commit from Source Control |
| The rule in `.github/instructions/project-template.instructions.md` (here, `AGENTS.md`) | Agents that write the commit message themselves, such as Copilot's |
| `/ship-plan` and `/run-issues` delete agent attribution lines from the pull request title and description they write (`workflow/templates/_pr-attribution.md`) | Attribution in the text the workflow writes |

Nothing checks for attribution or fails over it: no hook rewrites or refuses a commit, no CI job or required check fails a pull request, push or pipeline, and no workflow command reads a post back to remove a footer, such as the `_Generated by [Claude Code](…)_` line a Claude Code cloud session appends, or reports one. What gets through stays. A repository whose ruleset still requires a `Commit attribution` check, from a template version before v0.83.0, drops it from the required checks, or every pull request waits for a check no workflow reports; `.template/Update-Project.ps1` says so when its update removes the check.

## Stay Current

A project pins exact versions so that a build today matches a build next month: each package, each CI action (by commit SHA), the .NET SDK in `global.json`, and the template version in `.template-version` (from `_commit` in `.copier-answers.yml`). Pinned versions never update themselves; something has to notice each new upstream release and change the pin.

| What goes stale | How it's kept current |
|---|---|
| A GitHub project's CI actions, packages and .NET SDK | Dependabot, built into GitHub: `.github/dependabot.yml` turns it on, with nothing to install or sign up for. Each week it opens a pull request for newer versions that are at least three days old (its cooldown) — every update of one kind together, except a new release of the NCode Review action, which comes alone, and security updates in a pull request of their own per ecosystem — which CI tests and you merge. Dependabot doesn't offer a new .NET SDK major: moving the target frameworks to a new .NET major version is a planned migration, `/plan-migration` |
| A GitLab project's packages and .NET SDK | By hand; GitLab has no free built-in equivalent. Its CI images use floating tags such as `python:3` and the .NET SDK image's major-version tag, so they follow upstream on their own. A .NET job installs the SDK `global.json` selects with `build/Install-Dotnet.ps1`, so `global.json` is the one place its version moves |
| A project's template-owned files | [`.template\Update-Project.ps1`](#update-a-project), run in the project. `copier check-update`, run there too, tells whether a newer tag exists. On GitHub, the weekly `template-update` workflow opens an issue when one does ([The Update Notice](#the-update-notice)) |
| A repository or user profile with only the workflow installed (`workflow\Install-HybridWorkflow.ps1 -Repo` or `-User`) | By hand: re-run the installer from a clone at the newest tag. The version it has is in `.template-version` — at the repository root, or in `~\.claude\` and `~\.copilot\` for the profile |
| This template's generated workflow files | `tools/Update-Template.ps1` regenerates them from `workflow/templates`; `tests/Test-Template.ps1` fails when they're behind |
| This template's own CI actions, in `.github/workflows/test-template.yml`; the Node.js packages its tests use, the yaml and nunjucks packages `tests/Test-Template.ps1` runs for its YAML and `_exclude` checks, pinned in `tests/node/package.json` and its lock file; and the Python programs its tests run, the Copier CI installs and the pre-commit `tests/Test-GitHooks.ps1` runs through uvx, pinned in `tests/requirements.txt` | Dependabot in this repository |

The pins inside `template/` — the actions in `ci.yml.jinja` and in the `.github/actions/install-dotnet` action, and the SDK in `global.json` — are in merged files, which each project's Dependabot keeps current on its own. A template release that moves the same pin to a different version conflicts on that line (keep the newer version), so change a pin in the template only when you change that step anyway, or to keep new projects from starting far behind. The pins in the template-owned workflows, such as `scorecard.yml`, `tag-release.yml`, `template-update.yml` and `code-review-auto-merge.yml`, are replaced by each update instead, except that when a project's Dependabot moved one past the template's, the update keeps the project's newer pin and lists it under Kept. Keep those pins current here too, so a new project doesn't start behind.

A Dependabot pull request that only moves the NCode Review pin in `.github/workflows/code-review.yml` to a newer minor or patch release merges itself. `.github/workflows/code-review-auto-merge.yml` runs from the default branch on `pull_request_target` for Dependabot's pull requests from the repository itself, with only `contents: write` and `pull-requests: write`, and checks nothing out: it reads the update with `dependabot/fetch-metadata`, which must name `NCodeGroup/code-review` alone, checks through the API that every changed line is in a `.github/workflows/*.yml` file and is that action's `uses:` line, pinned to a full commit SHA with its `# vX.Y.Z` tag, and runs `gh pr merge --auto` for the commit it checked, with the first merge method that both the repository's settings and the active rules of the branch it merges into allow: a merge commit, else a rebase, else a squash. A ruleset's allowed merge methods and its "Require linear history" rule count; when no method is left, the run fails and says so. Classic branch protection's "Require linear history" can't be read with the workflow's token: a repository that sets it there should turn merge commits off in its settings, or require linear history in a ruleset instead. The bump then merges once the checks the default branch requires pass, and, where the ruleset requires an approval, once it is approved: where NCode Review's approver is set up, `code-review.yml` reviews Dependabot's pull requests by itself and the NCode Review Approver approves a clean review, so the bump merges with no person's action ([ADR-0041](template/docs/decisions/project-template/0041-ncode-review-reviews-and-approves-dependabots-pull-requests.md)); the workflow approves nothing. A major release, which can change the inputs the caller passes, a pull request that updates other dependencies too, and any other change wait for you. Dependabot puts every other action update of a week in one pull request, but `.github/dependabot.yml` gives `NCodeGroup/code-review` a group of its own, `ncode-review`, listed before the catch-all group, since Dependabot puts an update in the first group that matches it: so the bump comes in a pull request of its own whatever else moved. Auto-merge has to be allowed in the repository's settings, which `tools/Set-RepositoryBaseline.ps1` does ([Protect the Default Branch](#protect-the-default-branch)). A project without `code-review.yml` gets no such pull request, so the workflow never merges anything there; to stop it, `gh workflow disable code-review-auto-merge.yml`. It is the one exception to ADR-0006, "a person merges every pull request; an agent never does": `docs/decisions/project-template/0006-a-person-merges-every-pull-request.md` records its scope and why the rule's reason, nothing merging over a review no person read, doesn't apply to a pin bump to a release that was itself reviewed and merged in NCodeGroup/code-review.

Once the run pushes and comments `/review`, the stand-in completes NCode Review's `Code review` check run on the pushed commit, which `/run-feedback` reads with `gh api .../commits/<sha>/check-runs`, and gives the pull request the bot's review of the push: a nit; a later `/review` on a newer head gets an empty review, whose check run completes too. The test checks that the writer's fix is pushed to `add-farewell`, never forced, and changes nothing outside `src/` and `tests/`; that the writer's thread gets `Autopilot: fixed in <commit>`; that the run fixes the nit in a second round and answers it once with `Autopilot: fixed in <commit>`; that it comments `/review` after each push and asks for the check run on its last pushed commit; that it recommends the merge once, in a top-level `Autopilot:` comment after the `/review`; and that nothing is resolved, merged, marked ready or edited. It waits at least five minutes for the review, as the command does. `-Scenario review-with-footer` has the stand-in save each comment and thread reply the run posts with a Claude Code cloud session's `_Generated by [Claude Code](…)_` footer: the test checks that the run's `/review` comment after its last push keeps the footer and still asks NCode Review for its review, that the run deletes no comment and edits no `/review` comment, that no `Autopilot:` comment asks for `/review`, and that the merge recommendation comes after the last `/review`. `-Scenario protected-approval` seeds an NCode Review finding on `.github/workflows/ci.yml` and answers the run's question with `yes, all`, and the run must then push that change and reply `Autopilot: fixed in <commit>`. Run all three. Run it by hand after changing `/run-feedback` or a command it runs, such as `/address-feedback`, as `Test-RunIssues.ps1` says.

Every end-to-end test takes `-Tool copilot` to run its prompts in the Copilot CLI instead of Claude Code, on the same fixture with the same checks, since the fixture project has both tools' commands; each `-SetupOnly` checks that the Claude Code and Copilot copies of the commands it runs hold the queries, routes and replies its checks read. The checks on where a run works are the same in every tool: a run's worktree is `.claude/worktrees/<name>` on `worktree-<name>`. `resume-copilot` is a run an earlier Copilot version left on the branch `feedback-<number>` in the main checkout. The runner, `tests/e2e/Agent.ps1`, runs `copilot -p` with `--allow-all`, `--no-ask-user`, `--disable-builtin-mcps` (no GitHub MCP server, so the session posts only through the stand-ins) and `--output-format json`, in a `COPILOT_HOME` of its own under the work folder, so the session has none of your Copilot MCP servers, skills or instructions, with `COPILOT_ALLOW_ALL=true`, so the fixture project's skills and agents load, also on a resume. It signs in with `COPILOT_GITHUB_TOKEN`, `GH_TOKEN` or `GITHUB_TOKEN`, or else the token `gh auth token` prints, read before the `gh` stand-in shadows `gh`, and hides it from the session's shell with `--secret-env-vars`. A session with `--allow-all` could still reach a general token, so the runner warns when the token isn't `COPILOT_GITHUB_TOKEN`: set `COPILOT_GITHUB_TOKEN` to a fine-grained personal access token with only the Copilot Requests permission. A Copilot run also checks that the session ran the project's skill its prompt names and loaded no MCP server. `-Model` passes `--model` to either tool, and `-MaxBudgetUsd` caps a Copilot session with `--max-ai-credits` at 100 AI credits a dollar; the cost prints in USD with the AI credits, or, with a warning naming the file, as unknown or as at least what was read when a run's usage file can't be read. `-CheckOnly` checks the tool the run used. `tests/e2e/Test-AddressFeedback.ps1 -Tool copilot -Scenario resume-claude` has Copilot finish a Claude Code run in its worktree, and `-Scenario resume-copilot` under `-Tool claude` has Claude Code move a run an earlier Copilot version left on `feedback-<number>` into a worktree and finish it. CI checks the runner against stand-ins with `tests/Test-AgentRunner.ps1`.

## Publish the Template

Once, from this folder:

```powershell
git add -A
git commit -m "Create the project template"
git tag v0.1.0
gh repo create NCodeGroup/project-template --public --source . --remote origin --push
git push origin v0.1.0
```

Copier picks the newest tag, so a change reaches projects only once it is tagged and pushed.

---

**TL;DR:** `.\New-Project.ps1 -Path C:\src\<name> -CreateRemote` creates a project with `AGENTS.md`, `CLAUDE.md`, Claude Code permissions, the plan-then-execute commands and agents for Claude Code, Copilot Chat and Copilot CLI — switch between your Claude and Copilot plans at any time — CI, Dependabot, and optional .NET settings, then creates its repository on GitHub, public, and pushes. Add `-Visibility private` for a private repository. Every file has one of three owners: template-owned files are replaced on every update and never edited; merged files — settings whose tools can't include a second file — take the template's changes merged with the project's edits; and project-owned files, including the `AGENTS.md` index, are never touched. `.\.template\Update-Project.ps1`, run in a project, updates itself to the newest version first, then does all three and commits, or stops on a same-line conflict in a merged file. Dependabot keeps each GitHub project's actions, packages and SDK current through weekly pull requests. Change the workflow in `workflow/templates`, run `tools/Update-Template.ps1` and `tests/Test-Template.ps1`, then tag and push; this repository is its single source of truth. `.\Adopt-Project.ps1 -Path <repository>` brings an existing repository under the template.
