## Work in the plan's worktree

Each plan lives in its own git worktree, so several Claude Code sessions can work on different plans on this machine at once. Before anything else, move this session to the plan:

1. Run `git rev-parse --show-toplevel`. If the path contains `/.claude/worktrees/` and has a `PLAN.md`, this session is in the plan's worktree: go on with the task.
2. Otherwise list the plan worktrees: run `git worktree list --porcelain`, keep each `worktree` path under `.claude/worktrees/` that has a `PLAN.md`, and read each plan's title from its first line.
3. Choose the plan, in this order: the worktree whose folder name the command's arguments give; else the only plan worktree; else, when there is no plan worktree, the `PLAN.md` in the current checkout, worked on where it is — a plan written without a worktree, such as in Copilot. Switch into a chosen worktree with the `EnterWorktree` tool and its `path`. With several plan worktrees and none named, list them with their titles and stop to ask which one. With no plan anywhere, stop and say so.

From here on, the plan's folder is the repository root: run every command there, Done-when commands included. In a worktree, never edit files or run git in the main checkout. When you delegate to a subagent, give it the folder's absolute path and tell it to work only there.

## Task

Land the plan in `PLAN.md` the way this repository's Landing policy says: push its commits to the default branch or open its pull request, tag and publish its release, comment on and close its issue, and file its follow-ups as issues. Run it again at any time: each stage checks whether it is done and skips it, so a run that stopped partway, or a pull request that has merged since, carries on where it left off. Never force-push, rebase onto a moved default branch, move or delete a tag, or delete a release.

Extra instructions (may be empty): $ARGUMENTS

1. Read the state: run `pwsh -NoProfile -File .template/Get-PlanState.ps1` from the repository root. It prints `key: value` lines. Below, `<default>` is its `default` value, `<branch>` its `branch` and `<version>` its `release`. Stop and say what to run instead when `plan` is `-`; when `dirty` is `yes`; when `steps` shows an open, escalated or failed step (run orchestrate-plan, or replan-step); when `reviewed` isn't `current`, because the work changed since its last clean review or never had one (run review-plan-diff); or when `next` is `finish-plan`, because everything is done (run finish-plan).
2. Read the policy from the `landing` line: `integrate` is `direct` or `pull-request`, `release` is `none`, `tag` or `tag+release`, and `changelog` names the changelog file. `draft` is `yes`, which opens the pull request as a draft, or `no`. `follow-ups` is `issues`, which files the plan's follow-ups as issues in this repository, `none`, which files none, or a repository path such as `owner/repo` or `group/subgroup/project`, which files them there. `follow-up-label` names the label filed follow-ups get, in double quotes when it has a space; below, `<label>` is that name without the quotes. `gate` is `none` or the command to run before a push, in double quotes when it has a space; below, `<gate>` is that command without the quotes. `protect` is `none` or `hook`. `pr-format` is `none` or `<file>#<heading>`, in double quotes when it has a space: a file in the repository and the text of a Markdown heading in it, whose section states this project's pull-request conventions. When it isn't `none`, read that section, from the heading to the next heading of the same or a higher level, and stop when the file or the heading is missing: say to fix the `- pr-format:` line in the `## Landing` section of `AGENTS.md`. Read `PLAN.md`'s title, `Issue:` line, which names one issue or several separated by spaces, Goal, Decisions and `## Follow-ups`. When `release` isn't `none`, stop when `<version>` is `-`, because the plan has no `Release:` line, or when the changelog's first `## ` heading isn't `## <version>`. When `renumber` isn't `-`, another plan has landed `<version>`, or a later version, since this plan was written, so this plan moves to `<renumber>`. When `pr` is `-`, `CLOSED` or `OPEN`, drop the empty commits as item 5 says, change the `Release:` line of `PLAN.md` to `Release: <renumber>`, and append the step The Renumber Step below gives to the end of its Steps section, numbered in sequence; then stop, and say the release moves to `<renumber>` and that orchestrate-plan, review-plan-diff and ship-plan come next. When `pr` is `OPEN`, also say that the next ship-plan pushes the renumber step to that pull request, which must then merge with a merge commit, not by rebasing. When `tag` is `present`, it must already point at the commit this plan lands; otherwise stop, because a tag is never moved. When `protect` is `hook` and `integrate` is `direct`, stop: the `pre-push` hook refuses a push to `<default>`, so set `integrate: pull-request`. Stop when `draft` is neither `yes` nor `no`: say to set `- draft: yes` or `- draft: no` in the `## Landing` section of `AGENTS.md`. Stop when `follow-ups` is not `issues`, `none` or a repository path with a `/` and no spaces: say to fix the `- follow-ups:` line in the `## Landing` section of `AGENTS.md`.
3. With `integrate: direct`, stop when `behind` is more than 0: the default branch moved since the plan branched, so bring it in, run the checks and the review again, then ship. With `integrate: pull-request`, `behind` doesn't matter, because the pull request merges it.
4. Show the landing summary, then ask me once whether to go ahead and wait for my answer. The summary lists: the commits to land (`git log --oneline origin/<default>..HEAD`), and the empty `Plan:` and `Re-plan step` commits among them that will be dropped; or, when the branch holds a renumber step's merge, that they stay and the pull request must merge with a merge commit, not by rebasing; where they go: the default branch, or a new pull request from `<branch>` and whether it opens as a draft, or, when `pr` is `OPEN`, the open pull request, which takes the commits `git log --oneline origin/<branch>..HEAD` lists; the gate `<gate>` that runs before the push, unless `gate` is `none`; the pull request's title and description, when `pr-format` isn't `none`; the tag and the release; what each issue on the `Issue:` line gets; and each follow-up, which is filed as an issue labelled `<label>`, in this repository or in the one `follow-ups` names, once the plan has landed unless I name it as one to drop. With `follow-ups: none`, say instead that no follow-up is filed, and list them so I can record them where this project tracks its work. After my yes, append ` — dropped` to the line in `PLAN.md` of each follow-up I named, then run every stage below without asking again. `git push` may still ask for its own approval.
5. Drop the empty commits when `landed` is `no` and the branch has never been pushed (`git rev-parse --abbrev-ref '@{u}'` fails): `git rebase -f --no-keep-empty (git merge-base HEAD origin/<default>)`. It changes no file, so the review still matches. Skip it when the branch has an upstream, because rewriting pushed commits needs a force-push. Skip it too when `pr` is `OPEN`, because the pull request's branch is already pushed. Skip it too when `git rev-list --merges origin/<default>..HEAD` prints a commit, because the rebase would drop the merge a renumber step made.
6. Land the commits, unless `landed` is `yes`: Before the push in any of the first three bullets below, when `gate` isn't `none`, run the gate: run `<gate>; if (-not $? -or $LASTEXITCODE) { exit 1 } else { exit 0 }` in PowerShell from the repository root, with the longest timeout the shell allows, and judge it by its exit code alone, not its output. When it exits non-zero, stop before pushing: say the gate failed and show the last 30 lines of its output. When it passes but `git status --porcelain` then prints anything, stop too: the gate changed files, so the review no longer matches what would land.
   - `direct`: when `release` isn't `none` and `tag` is `absent`, tag the commit first: `git tag -a <version> -m <version>`. Then push the commits and the tag together, so both land or neither does: `git push --atomic origin HEAD:refs/heads/<default> refs/tags/<version>`, or `git push origin HEAD:refs/heads/<default>` when there is no tag. A rejected push means the default branch moved: stop, as in item 3.
   - `pull-request`, when `pr` is `-` or `CLOSED`: push the branch with `git push -u origin HEAD`, then open the pull request. Its title is the plan's title, and its description is two to five lines summarizing the plan's steps and Decisions. When `pr-format` isn't `none`, write the title and the description as its section says instead, such as a conventional-commit title or required headings, from the plan's title, Goal, steps and Decisions. Either way, the description ends with one `Closes <issue reference>` line for each reference on the plan's `Issue:` line, each on a line of its own, such as `Closes #25` and `Closes #24`. GitHub: `gh pr create --base <default> --head <branch> --title "<title>" --body-file <file>`. GitLab, when `host` is `gitlab`: `glab mr create --source-branch <branch> --target-branch <default> --title "<title>" --description (Get-Content -Raw <file>) --yes`. When the extra instructions say `draft`, or the `landing` line says `draft=yes`, open it as a draft: add `--draft` to either command.
   - `pull-request`, when `pr` is `OPEN`: when `git rev-list --count origin/<branch>..HEAD` prints more than 0, the branch holds commits the pull request doesn't have yet, such as a renumber step's merge: push them with `git push origin HEAD`, never forced, and say so; when that command fails because `origin` has no `<branch>`, push nothing and say so. When `git rev-list --merges origin/<default>..HEAD` prints a commit, say the pull request must merge with a merge commit, not by rebasing. Then stop here. Say the pull request waits for review and merge, give its URL, and say that running ship-plan again after the merge tags, publishes and closes what's left.
   - `pull-request`, when `pr` is `MERGED`: stop and give the state script's `next`. When the pull request merged into another base branch, as a stacked pull request does, say this branch lands once that branch reaches `<default>`, and to run ship-plan again then. Otherwise it merged without this branch's `HEAD`, because commits were added after it: say to land those commits from a new branch.
7. Tag when `release` isn't `none` and `tag` is still `absent`, as it is after a pull request merged. Tag the commit on the state script's `merge` line, the commit the pull request merged as. When `merge` is `-`, stop and say so: no merged pull request names the commit to tag. Run `git fetch origin`, then `git tag -a <version> -m <version> <commit>` and `git push origin refs/tags/<version>`.
8. Publish when `release` is `tag+release` and `published` isn't `yes`. Write the changelog's `## <version>` section, without its heading and up to the next `## ` heading, to a file. Then on GitHub: `gh release create <version> --verify-tag --title <version> --notes-file <file>`; on GitLab: `glab release create <version> --name <version> --notes-file <file>`.
9. File the follow-ups, unless `follow-ups` is `none`: then skip this stage, and item 12 lists them instead. Below, `<repo args>` is `--repo <owner/repo>` when `follow-ups` names a repository, and nothing when it is `issues`; and `#<number>` is written `<owner/repo>#<number>` for an issue in that repository. Take each line of `## Follow-ups` that doesn't end with `— filed as #<number>`, `— already tracked as #<number>` or `— dropped`. For each:
   - The title is the text before the first `: ` (the first 70 characters of the line when it has none); the rest is the body.
   - Search the open issues for the same work: `gh issue list <repo args> --state open --search "<title>" --json number,title --limit 10`, or `glab issue list <repo args> --search "<title>" --output json`. When one clearly covers it, file nothing and append ` — already tracked as #<number>` to the line.
   - Make the label once per run, before the first issue: `gh label create "<label>" --color FBCA04 --description "Work a plan found and did not do" <repo args>`, or `glab label create --name "<label>" --color "#FBCA04" --description "Work a plan found and did not do" <repo args>`, where an "already exists" failure is fine and leaves that label as it is. When it fails for another reason, file the issues without `--label "<label>"` and say so.
   - Write the body to a file: the body, a blank line, then `Found while planning <the Issue: references, or the plan's title>; it landed in <the link of the pull request, the release or the commit>.` When `follow-ups` names a repository, write each `Issue:` reference there as the issue's URL, from `gh issue view <number> --json url --jq .url` or the `web_url` of `glab issue view <number> --output json`, because `#<number>` would point into the other repository. Then `gh issue create <repo args> --title "<title>" --body-file <file> --label "<label>"`, or `glab issue create <repo args> --title "<title>" --description (Get-Content -Raw <file>) --label "<label>"`. Take the number from the URL it prints and append ` — filed as #<number>` to the line in `PLAN.md`, so a second run doesn't file it again.
   - When this run filed any and `issue-state` is `CLOSED`, because the pull request closed its issues, comment once on the first issue on the plan's `Issue:` line, with item 10's comment command: `Follow-ups filed from this plan: #<number> <title>, …`. When `issue-state` is `OPEN`, item 10's comments list them instead.
10. Close the issues when `issue-state` is `OPEN`. The `issue-states` line gives each issue on the `Issue:` line with its state, such as `#25=OPEN #24=CLOSED`: for each one marked `OPEN`, comment once, then close it, one comment per issue. The comment says where the change landed (the release, or the commit or pull request), summarizes the Goal in two to four sentences, names the other issues the plan covered, when it covered several, and lists the follow-ups: each filed one as `#<number> <title>`, and each one marked `— dropped` as plain text, or, with `follow-ups: none`, each one as plain text. GitHub: `gh issue comment <number> --body-file <file>`, then `gh issue close <number>`. GitLab: `glab issue note <number> --message (Get-Content -Raw <file>)`, then `glab issue close <number>`. Add `--repo <owner/repo>` for an issue in another repository. A pull request that merged with `Closes` has already closed its issues, so `issue-state` is `CLOSED` and this stage is skipped.
11. Write each comment, description, release note and issue body to a temporary file outside the repository with your file-writing tool, in a call of its own, and pass the file to the command. Never put the text in the command line. Delete the files in a separate command at the end.
12. Finish with each stage as done, skipped because it was already done, or waiting, the gate as passed or not run, with the links to the pull request, the release and the comment. Run the state script again and give its `next` as the next command: usually `/finish-plan`, which deletes `PLAN.md`, removes the plan's worktree and fast-forwards the default branch. With `follow-ups: none`, list the plan's follow-ups, each line in full, so they can be recorded where this project tracks its work.

## The Renumber Step

Fill in `<changelog>`, `<default>`, `<version>`, `<renumber>` and the step number `<N>`:

    ### [ ] <N>. Renumber the release to <renumber>
    - Files: `<changelog>` (edit)
    - Change: another plan landed `<version>` before this one. Run `git merge --no-commit --no-ff origin/<default>`. Then make `<changelog>` hold every section of the changelog on `origin/<default>`, unchanged and in order, with this plan's section above them under the heading `## <renumber>` instead of `## <version>`, and no conflict markers. When the merge leaves a conflict in any other file, run `git merge --abort` and escalate, naming those files. Commit note: the merge has already staged the files `origin/<default>` changed, which belong to this step; stage only `<changelog>`, and the step's commit records the merge.
    - Done when: `$h = @(Get-Content <changelog> | Where-Object { $_ -match '^## ' }); $o = @(git show origin/<default>:<changelog> | Where-Object { $_ -match '^## ' }); $in = (git rev-parse -q --verify MERGE_HEAD) -or ((git merge-base HEAD origin/<default>) -eq (git rev-parse origin/<default>)); if ($in -and -not (git diff --name-only --diff-filter=U) -and $h[0] -eq '## <renumber>' -and $h[1] -eq $o[0]) { exit 0 } else { exit 1 }`
