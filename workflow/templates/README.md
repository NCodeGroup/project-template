# Plan-and-Execute Templates

Source templates for the plan-and-execute workflow — the single source of truth for every prompt and agent file. They are tool-neutral: [Install-HybridWorkflow.ps1](../Install-HybridWorkflow.ps1) turns them into Claude Code commands and subagents, VS Code prompt files and custom agents, and Copilot CLI skills and agents; [New-PlanPrompt.ps1](../New-PlanPrompt.ps1) composes them for pasting into any chat; [Invoke-PlanSteps.ps1](../Invoke-PlanSteps.ps1) runs `execute-step` and `replan-step` from them. The workflow itself, and how to choose between its variants, is in personal-notes' [plan-and-execute.md](https://github.com/polewskm/personal-notes/blob/main/ham-radio/shack/shack-pc/local-ai/plan-and-execute.md).

## Prompt Templates

Each prompt has a small front-matter header (`description`, `argument-hint`, `role`, `append-format`, and optionally `worktree`, `targets` and `command`) and a body with one `{{INPUT}}` placeholder for your request. Planning templates with `append-format: true` get [_plan-format.md](_plan-format.md) appended, so every plan comes out in the same parseable shape. `targets: Claude` limits a template to the installer targets it names, comma-separated from `VSCode`, `Claude` and `CopilotCli`; without it a template goes to all three. `New-PlanPrompt.ps1 -List` shows each template's targets. `command` names the command, prompt file and skill a template installs as, when that differs from its file name: `run-issues-copilot.md`, `address-feedback-copilot.md` and `run-feedback-copilot.md` have `targets: VSCode, CopilotCli` and `command: run-issues`, `command: address-feedback` and `command: run-feedback`, so those commands run them in Copilot while `run-issues.md`, `address-feedback.md` and `run-feedback.md` stay Claude Code's. A Claude Code template and its Copilot variant share their common text through partials ([Other Files](#other-files)). The installer stops when two templates install the same command for the same target.

### Plan Worktrees

In every tool, each plan lives in its own git worktree, `.claude/worktrees/<name>/` on the branch `worktree-<name>`, so several sessions can work on different plans in one clone at once and the main checkout is never switched or edited. A template's `worktree` field says what its command does with the plan's worktree. Each tool gets its own sections: the installer puts the matching one before the command's body, followed by a `## Task` heading, in the Claude Code commands, the VS Code prompt files and the Copilot CLI skills, and the Copilot sections go into the VS Code agents and the `plan-executor` agent too. Claude Code's sections move the session into the worktree with the `EnterWorktree` and `ExitWorktree` tools. A Copilot session can't move its shell's working folder, so each Copilot section names `<plan folder>`, the worktree's absolute path, and has every command start with `Set-Location -LiteralPath '<plan folder>';`, gives file tools absolute paths and tells every subagent the folder.

| `worktree` | Sections | Templates | The command |
|---|---|---|---|
| `create` | [_claude-worktree-create.md](_claude-worktree-create.md), [_copilot-worktree-create.md](_copilot-worktree-create.md) | The `plan-*` templates and `handoff-plan` | Enables `.githooks` and records the session's push branch from the main checkout, then creates `.claude/worktrees/<name>/` (with the `EnterWorktree` tool in Claude Code, with `git worktree add --no-track` in Copilot, which never switches the main checkout) before it researches, plans there, keeps `PLAN.md` untracked, and marks the worktree with an empty `Plan: <title>` commit so Claude Code asks before removing it; Copilot's cloud agent creates no worktree and plans in its own checkout |
| `analyze` | [_claude-worktree-analyze.md](_claude-worktree-analyze.md), [_copilot-worktree-analyze.md](_copilot-worktree-analyze.md) | `analyze-architecture`, `analyze-decision` | Creates a worktree as `create` does, before it researches, keeps `ANALYSIS.md` untracked and ignored, and commits a decision record there as `Record decision: <title>`, so the plan made in the same worktree lands it; Claude Code makes it with `git worktree add` and enters it with `EnterWorktree` and its `path`, so it keeps the worktree without an empty commit |
| `join` | [_claude-worktree-join.md](_claude-worktree-join.md), [_copilot-worktree-join.md](_copilot-worktree-join.md) | `orchestrate-plan`, `execute-step`, `replan-step`, `review-plan-diff`, `ship-plan` | Moves the session into the plan's worktree (Claude Code), or works only in its folder (Copilot) — the one its arguments name, or the only one — before it starts; with no plan worktree, works on a `PLAN.md` in the current checkout |
| `finish` | [_claude-worktree-finish.md](_claude-worktree-finish.md), [_copilot-worktree-finish.md](_copilot-worktree-finish.md) | `finish-plan` | Finds the plan's worktree — the session's own, the one its arguments name, or the only one — without entering it, removes it with the `ExitWorktree` tool (Claude Code) or `git worktree remove`, clears a stale lock or a leftover folder, including one Windows' path limit left behind, and fast-forwards the default branch without switching a main checkout that holds other work |

A command without the field works where the session is, or makes its own worktrees. `run-issues` and `run-issues-copilot` have no field: each makes every issue's worktree itself with `git worktree add`, `.claude/worktrees/issue-<number>`, works in it (Claude Code enters it with `EnterWorktree` and its `path`; Copilot starts each command there), and removes it through `finish-plan`; both run the next entry ahead in its own worktree while a pull request waits. Nor has `address-feedback`, or `address-feedback-copilot`: each makes a pass's worktree, `.claude/worktrees/feedback-<number>`, itself with `git worktree add`, and removes it once the pass's fixes are pushed. `New-PlanPrompt.ps1` never gets a section. The `plan-executor` subagent inherits the orchestrator's worktree in Claude Code, where `isolation: worktree` would give it a worktree of its own instead; in Copilot the orchestrator tells every subagent the plan's folder. Whatever the command, the plan's branch keeps its name; with a push branch, as [_push-branch.md](_push-branch.md) says, `ship-plan` pushes it to that branch instead.

## Template Syntax

| Token | Where | Replaced with |
|---|---|---|
| `{{INPUT}}` | Prompt bodies | Your request; `$ARGUMENTS` in Claude Code commands; `${input:details:<hint>}` in VS Code prompt files; a description of the command's argument in Copilot CLI skills |
| `{{PROMPT:name\|input}}` | Agent bodies | The body of prompt `name` with `{{INPUT}}` set to `input` |
| `{{BODY:name\|input}}` | Prompt bodies | The body of prompt `name` with `{{INPUT}}` set to `input`, without the plan format; `plan-issue` uses it to include each `plan-*` checklist |
| `{{PLANNER_AGENT}}`, `{{IMPLEMENTER_AGENT}}`, `{{REVIEWER_AGENT}}`, `{{ORCHESTRATOR_AGENT}}`, `{{EXECUTOR_LABEL}}` | Agent templates | Agent names and the executor description for the variant being installed |
| `{{PLANNER_MODEL}}`, `{{REVIEWER_MODEL}}`, `{{EXECUTOR_MODEL}}`, `{{FAST_EXECUTOR_MODEL}}` | Agent front matter | `-PlannerModel`, `-ReviewerModel`, and `-LocalModel`/`-FastLocalModel` (Local) or `-CopilotExecutorModel`/`-CopilotFastModel` (Copilot) |
| `{{CLAUDE_EXECUTOR_MODEL}}`, `{{CLI_EXECUTOR_MODEL}}` | `plan-executor` templates | `-ClaudeExecutorModel`, `-CliExecutorModel` |
| `{{STATE_SCRIPT}}` | Prompt bodies | The command that runs `Get-PlanState.ps1`: `pwsh -NoProfile -File .template/Get-PlanState.ps1`, or the copy in `~\.claude\` or `~\.copilot\` for `-User` |

To add a prompt template, create `<name>.md` with the same four header fields, plus `worktree: create` when its command writes a new `PLAN.md`, `worktree: join` when it works on one, or `worktree: finish` when it closes one; `New-PlanPrompt.ps1 -List` and the installer pick it up automatically.

New projects get generated copies of these files under `template/` ([What a Project Gets](../../README.md#what-a-project-gets)). After changing a template here, run `tools/Update-Template.ps1` and `tests/Test-Template.ps1` from the repository root, then commit, tag and push a new version; projects pick it up with `Update-Project.ps1`.

---

**TL;DR:** Twenty-nine prompt templates for twenty-six commands (planning, issue triage, template updates, analysis, review, orchestration, autopilot, pull request feedback, re-planning, execution, finishing) and four variant-neutral VS Code agents, written once and installed into Claude Code, VS Code and Copilot CLI by `Install-HybridWorkflow.ps1`. Every planning prompt ends with the same PLAN.md contract, and the executor prompt escalates with `[?]` instead of improvising, so any planner and any executor can be combined.
