## The Changelog

The changelog is the file the `changelog` key of `AGENTS.md`'s `## Landing` section names, `CHANGELOG.md` by default. Read it before you write its step. It follows Keep a Changelog 1.1.0 (https://keepachangelog.com/en/1.1.0/) when it has a `## [Unreleased]` heading or a heading such as `## [1.4.0] - 2026-10-28`. The state script prints `changelog-format: keep-a-changelog` for such a file, `other` for a changelog in any other format, and `missing` when there is no file.

A Keep a Changelog file holds, in order: `# Changelog`, its preamble, `## [Unreleased]`, one `## [<number>] - <date>` section per release, newest first, and the link reference definitions. `<number>` is the version without a leading `v` (`1.4.0` for `v1.4.0`). `<date>` is the day the section is written, as `Get-Date -Format yyyy-MM-dd` prints it. A section's entries are `- ` bullets written for the project's users. An entry for a change that breaks how existing users work starts with `**Breaking:**` and says what to change, except in a pre-release project, below; an entry ends with a link to the issue it closes and, when one records the decision, its decision record, such as `([#42](<web>/issues/42), [ADR-1007](docs/decisions/1007-<title>.md))`; and a dependency update that closes a vulnerability names its advisory, such as `GHSA-xxxx-xxxx-xxxx` or the CVE, under `### Security`. They are grouped under these headings, in this order, and each heading appears only when it has an entry: `### Added` (new commands, files, settings, options or output), `### Changed` (changes to behavior or documentation), `### Deprecated`, `### Removed`, `### Fixed` (behavior that was wrong) and `### Security` (a vulnerability or exposure closed). A section has at most one of each heading: an entry goes under its group's heading when the section already has it, and is never put under a second heading of the same name, also when two sides' changes to the changelog are combined. Two pull requests that each add the same heading to `## [Unreleased]` merge without a conflict and leave the heading twice; the state script names each heading a section has more than once as `changelog-duplicates: <section> <heading>`, such as `[Unreleased] Changed`, joined by `, `, or prints `-`. The link reference definitions come newest first. The first is `[unreleased]: <web>/compare/<newest tag>...HEAD`. Then each release has `[<number>]: <web>/compare/<previous tag>...<tag>`, or `[<number>]: <web>/releases/tag/<tag>` for the first release. `<web>` is the repository's web address: `git remote get-url origin` written as `https://<host>/<path>` without `.git`. On GitLab, the links use `<web>/-/compare/` and `<web>/-/tags/<tag>`. Tags keep the project's prefix, such as `v1.4.0`. A file with no release yet has no link reference definitions.

A project is pre-release while the `pre-release` key of `AGENTS.md`'s `## Landing` section is `untracked` and no tag `git tag --list --merged HEAD` prints is a stable version: shaped like `v1.2.3` or `1.2.3`, with a major version of 1 or more. The state script prints `pre-release: yes` for it, and `no` otherwise, also for a plan whose `Release:` line names a stable version. Nothing a pre-release project has released or stored has a reader that must keep working, so its changelog describes the product as it is, not its changes, as ADR-0015 in `docs/decisions/project-template/` records. It is a Keep a Changelog file whose `## [Unreleased]` holds only `### Added`, the capabilities, and `### Security`, the security posture and protections, and that has no release section and no link reference definitions: a release's notes are that section as it stands. Its preamble ends with the line `Until the first stable release, the [Unreleased] section describes the product as it is, not its changes.` An entry says in the present tense what the product does, never how it differs from an earlier state: no `**Breaking:**` label, no "now", "no longer", "previously", "renamed" or "replaces" set against an earlier state, no name of a removed member, and no upgrade or migration note. It ends with links to the issues and decision records behind it, such as `([#42](<web>/issues/42), [ADR-1007](docs/decisions/1007-<title>.md))`. A pre-release project's commit subjects and pull request titles carry no conventional-commit `!` marker and no `BREAKING CHANGE:` footer either, as ADR-0015 says.

The plan's last step writes the plan's entries, for every plan:

- In a pre-release project, whatever its `changelog-format` and with or without a `Release:` line: create the file when it is missing, as `missing` below says, with the preamble's pre-release line last before `## [Unreleased]`. Then edit `## [Unreleased]` in place, so it describes the product once the plan has landed: add an entry for each capability or protection the plan adds, rewrite the entry of each one the plan reshapes, keeping its links and adding the plan's issue, and delete the entry of each one it removes. A fix to behavior no stable release shipped adds nothing, unless an entry no longer matches the code. Put each entry under `### Added` or `### Security`, and write no other heading, release section or link. A changelog that isn't a catalog yet, because it has another heading under `## [Unreleased]`, a release section or another format, is left as it is, and the plan lists this follow-up under `## Follow-ups`, filling in `<changelog>`: `Describe the product as it is in the changelog: rewrite <changelog> as the pre-release catalog ADR-0015 describes, so each plan edits it in place.`
- The plan whose `Release:` line names the first stable version, such as `v1.0.0`, in a project whose Landing section says `pre-release: untracked`, ends the pre-release: its last step inserts `## [<number>] - <date>` right below `## [Unreleased]`, moves every catalog entry into it, edited for the plan's own work as the bullet above says, so that version's notes describe everything it ships, leaves `## [Unreleased]` empty, deletes the preamble's pre-release line, and adds `[unreleased]: <web>/compare/<tag>...HEAD` and `[<number>]: <web>/releases/tag/<tag>`. With `release: none`, the first plan whose state script prints `pre-release: no` while the Landing section says `untracked` and the changelog has no release section does this, with the first stable tag's number and date (`git log -1 --format=%as <tag>`), before it writes its own entries as `keep-a-changelog` says. From then on, the bullets below apply.
- `missing`: create the file, then write to it as for `keep-a-changelog`. It starts with these lines, each followed by a blank line except the last: `# Changelog`, then `All notable changes to this project will be documented in this file.`, then `The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).`, then `## [Unreleased]`.
- `keep-a-changelog`, without a `Release:` line: add the entries under `## [Unreleased]`, putting each in its group, and add to a group that is already there instead of writing its heading again. When `changelog-duplicates` names a heading of `[Unreleased]`, the step also merges that heading's groups into one, at the first one's place, keeping every entry in order.
- `keep-a-changelog`, with a `Release:` line: insert `## [<number>] - <date>` right below `## [Unreleased]`. Put in it every entry `## [Unreleased]` held and the plan's own, in one set of groups with each heading once, and leave `## [Unreleased]` empty. Set the `[unreleased]` link to compare the new tag with `HEAD`, and add the new version's link above the previous version's.
- `other`, with a `Release:` line: add that version's section at the top, in the style of the sections below it.
- `other`, without a `Release:` line: leave the file as it is.

Write the step so the executor copies text: it gives the heading, each entry under its group, and each link line in full. In a pre-release project, it gives each entry to add in full, and each entry to rewrite or delete by its first words and, for a rewrite, its new text in full. Only `<date>` is left to the executor, with the `Get-Date` command. Never reformat a changelog in another format, or an older section of any changelog, unless the request asks for it, as an adopted project's follow-up does; a heading that `changelog-duplicates` names in an older release section stays as it is. A plan that converts a changelog keeps every entry's text. It dates each version's heading with its tag's date (`git log -1 --format=%as <tag>`), puts each entry in one group, and adds the preamble, `## [Unreleased]` and the link reference definitions.

A project can have version tags its changelog has no section for, such as the releases it made before a plan first created the changelog. They are the tags `git tag --list --merged HEAD` prints that are shaped like `v1.2.3` or `1.2.3` and match no release heading in the changelog, such as `## [1.2.3] - <date>` or `## v1.2.3`. In a project whose Landing section says `pre-release: untracked`, a tag below the first stable version never counts, because the pre-release changelog has no release section by design. The state script prints them as `changelog-backfill: <oldest>..<newest>`, as the tag alone when there is one, or as `-` when there is none, and `Update-Project.ps1` and the template's `Adopt-Project.ps1` print a request to backfill them. When there are any, and the plan isn't that backfill, list this follow-up under `## Follow-ups`, filling in `<changelog>` and `<range>`: `Backfill the changelog from past releases: add a section to <changelog> for each version tag in <range> that has none, from the tag's release notes, so the changelog covers the project's full release history.` A backfill plan writes one `## [<number>] - <date>` section for each such tag, dated with the tag's date (`git log -1 --format=%as <tag>`) and placed among the other sections by version, newest first; in a changelog of another format, it writes it in the style of the sections there. The planning session fetches each tag's release notes, with `gh release view <tag> --json body --jq .body` on GitHub or `glab release view <tag>` on GitLab, and copies the entries into the plan's steps, because the executor never calls `gh` or `glab`. For a tag without a release, it summarizes `git log --oneline <previous tag>..<tag>`, or `git log --oneline <tag>` for the first tag, into entries for the project's users. It puts each entry in one group and keeps the project's own marker for a breaking change, such as a `**Breaking:**` prefix. It adds each version's link line in order, and the `[unreleased]` link when the file has none; a changelog of another format gets no links. A backfill of many tags spreads them over several steps, a few versions each.
