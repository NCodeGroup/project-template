## Finish the plan's worktree

Each plan lives in its own git worktree under `.claude/worktrees/<name>/`, on the branch `worktree-<name>`. This command also removes that worktree, from the main checkout, so the task below runs in two places: its steps 1 to 3 in the worktree, and its steps 4 and 5 in the main checkout. `<main checkout>` is the path on the first `worktree` line of `git worktree list --porcelain`. A Copilot session can't change the folder its shell starts in, so start every command with `Set-Location -LiteralPath '<the folder it runs in>';` and give file tools absolute paths.

1. Find the worktree. When the command's arguments name one, run `git worktree list --porcelain`, find the `worktree` path under `.claude/worktrees/` with that folder name, and use it — even when this session is already in a different worktree. Otherwise run `git rev-parse --show-toplevel`: when the path contains `/.claude/worktrees/`, this session is in it. Otherwise list the plan worktrees the same way; with several and none named, list them with their branches and stop to ask which one; with none, do the whole task where this session is.
2. Do the task's steps 1 to 3 in the worktree: in it, as written; from the main checkout, with `git -C <worktree path>` and the state script's `-Path <worktree path>`, deleting `<worktree path>/PLAN.md`, and `<worktree path>/ANALYSIS.md` when it exists. The plan's branch is `worktree-<name>`, even when the state script's `branch` is `-`.
3. Then remove the worktree from the main checkout: run `git -C '<main checkout>' worktree remove '<worktree path>'`.
4. When git says the worktree is locked by `claude session <name> (pid <N>)`, check whether that process runs (`Get-Process -Id <N>`). When it runs, stop and ask me to end that session. When it doesn't, run `git worktree unlock <worktree path>` and remove the worktree again. When removing fails with "Permission denied", "Access is denied" or a folder in use, stop and ask me to close the terminals, editors and sessions open in that folder, including this session when it was started in that folder, then run `/finish-plan <name>` from a session in the main checkout. When removing fails with "Filename too long", a path in the worktree passes Windows' 260-character limit, and git has already unregistered the worktree and deleted what it could. The task's checks showed nothing is lost, so delete the folder with `Remove-Item -LiteralPath <worktree path> -Recurse -Force`, which handles long paths, and in the summary ask me to run `git config --global core.longpaths true`, so git removes such a worktree itself next time.
5. In the main checkout, run `git worktree list --porcelain`. When the worktree is still listed, run `git -C '<main checkout>' worktree remove '<worktree path>'`, and go back to item 4 when git reports a lock, a folder in use or "Filename too long". Then run `git worktree prune`. When the worktree's folder is still there and empty, delete it. When it still holds files and `Get-ChildItem -LiteralPath <worktree path> -Recurse -Force | Where-Object { $_.FullName.Length -ge 248 }` lists any, removal stopped at Windows' path limit: handle it as item 4 says for "Filename too long". Otherwise, when it still holds files, stop and list them.
6. Do the task's steps 4 and 5 in the main checkout. When it isn't on the default branch, run `git fetch origin <default branch>:<default branch>` instead of switching and pulling: it only fast-forwards, and leaves the work checked out there alone. Delete `worktree-<name>` only after that fast-forward.

From here on, never run commands in the removed worktree's folder.
