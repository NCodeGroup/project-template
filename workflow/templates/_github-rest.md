A session's network can refuse GitHub's GraphQL API, as a Claude Code cloud session's proxy does: then `gh api graphql` and the `gh pr`, `gh issue` and `gh release` commands, which use GraphQL, fail with an error that says GitHub GraphQL is not available, while `gh api` with a REST path still works. After a `gh` command fails that way, run each `gh pr`, `gh issue`, `gh release` and `gh api graphql` command these instructions give in its REST form below for the rest of this run, with `gh api`, and read its answer as that command's: `{owner}/{repo}`, which `gh api` fills in from the clone's `origin`, becomes the `<owner>/<repo>` of the command's `--repo` when it has one, and a body comes from the same file, through `-F body=@<file>`. `gh pr view <number> --json …` is `gh api repos/{owner}/{repo}/pulls/<number>`: `html_url` is the `url`, `state` is `open` or `closed`, and `MERGED` when `merged` is true, `draft` is `isDraft`, `head.ref` is `headRefName`, `head.sha` is `headRefOid`, `base.ref` is `baseRefName`, `body` is the description, and `isCrossRepository` is true when `head.repo.full_name` differs from `base.repo.full_name`. `gh pr list --state open --search "<number> in:body"` is `gh api --paginate "repos/{owner}/{repo}/pulls?state=open&per_page=100"`, keeping those whose `body` names the issue. `gh pr create --base <default> --head <branch> --title <title> --body-file <file>` is `gh api repos/{owner}/{repo}/pulls -f base=<default> -f head=<branch> -f title=<title> -F body=@<file>`, with `-F draft=true` for `--draft`, and its `html_url` and `number` are the new pull request's URL and number. `gh pr edit <number> --body-file <file>` is `gh api -X PATCH repos/{owner}/{repo}/pulls/<number> -F body=@<file>`. `gh pr comment <number> --body-file <file>` and `gh issue comment <number> --body-file <file>` are `gh api repos/{owner}/{repo}/issues/<number>/comments -F body=@<file>`, whose `html_url` is the comment's URL, ending in `#issuecomment-<id>`. `gh issue view <number> --json …` is `gh api repos/{owner}/{repo}/issues/<number>` for its `title`, `body`, `labels`, `state` (`open` or `closed`, which `gh` prints as `OPEN` or `CLOSED`), `assignees` and `html_url`, and `gh api --paginate "repos/{owner}/{repo}/issues/<number>/comments?per_page=100"` for its comments, each with `user.login`, `body` and `html_url`. `gh issue list --state open …` is `gh api -X GET search/issues -f q='repo:<owner>/<repo> is:issue is:open <qualifiers>' -f per_page=<limit>`, whose `items` are the issues: each `--label <name>` is `label:"<name>"`, `--milestone <title>` is `milestone:"<title>"`, `--assignee <login>` is `assignee:<login>` and `--search <words>` is the words, and without `--repo`, `<owner>/<repo>` is what `gh api repos/{owner}/{repo} --jq .full_name` prints. `gh issue create --title <title> --body-file <file> --label <label>` is `gh api repos/{owner}/{repo}/issues -f title=<title> -F body=@<file> -f 'labels[]=<label>'`, `gh issue edit <number> --body-file <file>` is `gh api -X PATCH repos/{owner}/{repo}/issues/<number> -F body=@<file>`, and `gh issue close <number>` is `gh api -X PATCH repos/{owner}/{repo}/issues/<number> -f state=closed -f state_reason=completed`. `gh release view <tag> --json body --jq .body` is `gh api repos/{owner}/{repo}/releases/tags/<tag> --jq .body`, and `gh release create <version> --verify-tag --title <version> --notes-file <file>` is `gh api repos/{owner}/{repo}/git/ref/tags/<version>`, which fails when origin has no such tag, then `gh api repos/{owner}/{repo}/releases -f tag_name=<version> -f name=<version> -F body=@<file>`. A `gh api graphql` query that reads a pull request's review threads, top-level comments and review summaries is four REST reads, each of every page, so a stop for a `hasNextPage` that is `true` doesn't apply: `gh api "repos/{owner}/{repo}/pulls/<number>/ccr/review_threads"`, the proxy's own route, for the threads, each with `resolved` (`isResolved`), `outdated` (`isOutdated`), `path`, `line` and `comment_ids`, the ids of its comments, oldest first; `gh api --paginate "repos/{owner}/{repo}/pulls/<number>/comments?per_page=100"` for those comments, matched by `id`, each with `user.login`, `user.type` (`Bot` for a bot, as `__typename` says), `author_association`, `body` and `html_url`; and `gh api --paginate "repos/{owner}/{repo}/issues/<number>/comments?per_page=100"` and `gh api --paginate "repos/{owner}/{repo}/pulls/<number>/reviews?per_page=100"` for the top-level comments and the review summaries, with the same fields; the pull request's `state` comes from `gh api repos/{owner}/{repo}/pulls/<number>`, as above. When the threads route fails, read the threads with the GitHub MCP tool `pull_request_read` and its method `get_review_comments` when the session has it, whose threads carry `isResolved`, `isOutdated` and their comments; without it, stop, and say that this session can read no review thread, because GitHub's REST API doesn't say whether a thread is resolved. The `addPullRequestReviewThreadReply` mutation that replies on a thread is `gh api repos/{owner}/{repo}/pulls/<number>/comments/<id>/replies -F body=@<file>`, where `<id>` is the thread's first comment's id, the first of its `comment_ids` or the number after `#discussion_r` in its URL, or the GitHub MCP tool `add_reply_to_pull_request_comment` with that id as `commentId`.
