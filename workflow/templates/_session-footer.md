A session's own tooling can add agent attribution to what it posts, on GitHub or GitLab, whichever AI agent, assistant or model runs the session: a Claude Code cloud session appends a line `---` and then a footer line `_Generated by [Claude Code](https://claude.ai/code/…)_` to each pull request description, issue, comment and review-thread reply it creates, through `gh` and the GitHub MCP tools alike, and other agents, such as Copilot's coding agent, Codex, Cursor, Devin, Jules or GitLab Duo, can append a line of their own that says the text was generated, written or created with or by an AI tool, or a link to the agent's session or task, while `gh` or `glab` in a local session appends nothing. So straight after each command that creates or edits a pull request or merge request description, an issue, or a top-level comment or note, read back what was saved, from the repository it went to. On GitHub: `gh pr view <number> --json body --jq .body` for a pull request, `gh issue view <number> --json body --jq .body` for an issue, each with the `--repo <owner/repo>` the command that posted had, when it had one, or `gh api "repos/<owner>/<repo>/issues/comments/<id>" --jq .body` for a comment, where `<owner>/<repo>` is the part of the URL the command printed between `github.com/` and `/issues/` or `/pull/`, and `<id>` is the number after `#issuecomment-` in it. On GitLab: the `description` in what `glab mr view <number> --output json` prints for a merge request or `glab issue view <number> --output json` prints for an issue, each with the `--repo <group/project>` the command that posted had, when it had one, or the `body` in what `glab api "projects/:id/merge_requests/<number>/notes/<id>"` prints for a note, with `issues` in place of `merge_requests` for a note on an issue and, for a note in another project, that project's URL-encoded path, such as `group%2Fproject`, in place of `:id`, where `<id>` is the number after `#note_` in the URL the command printed, or the `id` the API returned. When the last lines of it that aren't blank are agent attribution, each a line that starts, after any symbols or underscores, with words such as `Generated with`, `Generated by`, `Created by` or `Made with` and then an AI tool, agent or model, such as `[Claude Code`, Copilot, Codex, Cursor, Devin, Gemini, Grok or GitLab Duo, or a line that holds only a link to an agent's session or task, such as a `claude.ai/code/session_`, `chatgpt.com/codex/tasks/`, `cursor.com/agents/`, `app.devin.ai/sessions/` or `jules.google.com/task/` link, remove those lines, the `---` line above them, when there is one, and the blank lines between and after them, and keep every other line as it was. Remove it in that same repository, through a route that doesn't append it again. On GitHub, use the GitHub MCP tools when the session has them, because in a Claude Code cloud session an edit through `gh` appends the footer again: `update_pull_request` with the new body for a pull request, `issue_write` with `method: update` and the new body for an issue, or `update_issue_comment` with the comment's id and the new body for a comment; without them, write the new body to a file and run `gh pr edit <number> --body-file <file>`, `gh issue edit <number> --body-file <file>` or `gh api -X PATCH "repos/<owner>/<repo>/issues/comments/<id>" -F body=@<file>`, with the same `--repo`. On GitLab, write the new text to a file and run `glab mr update <number> --description (Get-Content -Raw <file>)`, `glab issue update <number> --description (Get-Content -Raw <file>)` or `glab api --method PUT "projects/:id/merge_requests/<number>/notes/<id>" -F body=@<file>`, with the same `--repo`, project and `issues` as the read-back. Then read it back once more; when the attribution is still there, the route appended it again: on GitHub, try the other route once, `gh` after the GitHub MCP tools or the GitHub MCP tools after `gh`, and when it is still there, or there is no other route, as on GitLab, leave it and list it in your report, and for a pull request or merge request description also say that the `Commit attribution` check may fail until a person deletes those lines. Two posts are exceptions. Never edit a `/review` comment, even when it came back with attribution: the `/review` request reads it back itself and deletes it when anything was appended, because NCode Review acts only on the comment as it was created, so an edited `/review` comment requests no review. A reply on a review thread is the other exception: on GitHub nothing a Claude Code cloud session can call edits one without its footer, so post each reply as these instructions say anyway, because every finding still gets its reply, and list the replies in your report as ones that may carry the footer; on GitLab, a reply on a discussion is a note, read back and edited as above with `discussions/<discussion id>/notes/<id>` in place of `notes/<id>`.
